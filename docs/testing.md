# Testing

The `NS3_*` debug hooks and the probe tools. **These are the testing strategy — there are no unit tests.** Split out of `CLAUDE.md`.

## Debug env hooks

**Debug env hooks** (mirror the v1 ones): `NS3_KIT=nova|tony|henry|sanjit|kovacs|leon|anders|hammy|ayaan`, `NS3_AUTOFIRE=<sec>`, `NS3_AUTOWALK="x,z"`, `NS3_GODMODE=1`, `NS3_SUPER=1` (start with Super charged), `NS3_CUBES=<n>` (start carrying n power cubes), `NS3_SHOTS="prefix:t1,t2,..."` (match-time screenshots, then quits; **give an absolute prefix** — a relative one now lands in `user://` rather than writing into the project, where the next import used to sweep it up as a game asset, and either way the path it wrote is printed; a fractional time keeps its decimals in the file name — `prefix_7.06.png` — so a burst can catch a 0.12 s wind-up instead of every shot in one second overwriting the last; and both this and `NS3_MENU_SHOT` **force a draw when the window cannot draw**, because the engine never draws an occluded, minimized or off-Space window and `get_image()` then returns the last frame it did draw — a harness run under a browser window came back as nine identical shots), `NS3_END=<sec>` (end the match this long after FIGHT!, with whatever placement the player has by then — the results card is otherwise only reachable by surviving or dying at an unpredictable moment, which made it the one screen `NS3_SHOTS` could not catch; pair them, remembering `NS3_SHOTS` times include the 7s `PREMATCH`), `NS3_KILL=<sec>` (eliminate the player this long after FIGHT! — the sibling of `NS3_END` and for the same reason: going down happens at an unpredictable moment, so the knockdown, the results card a Showdown death raises and the Nobles Cup respawn three seconds later were all unshootable. In Cup this is the only practical way to see an arrival: a whole match yields two or three deaths and none of them where you are looking), `NS3_MENU_SHOT=<path.png>` (menu screenshot, then quits; combine with `NS3_MENU_SCREEN=lobby|roster|modes|shop|season|wifi|settings|profile|loading` — the old `brawlers`/`fighters`, `pass`, `road`, `friends` and `events` all still resolve as aliases; `loading` is not a screen in the stack but the transition out of the menu, so it presses PLAY and shoots inside `LoadingScreen.MIN_SHOW` — and `NS3_MENU_DETAIL=<kit>`, which now *selects* that fighter, since home's flanks are the detail view; and `NS3_MENU_PROGRESS=trophies:2000,tier:11,tokens:300,premium:1,claimed:1,starters:1`, which seeds progress IN MEMORY and never writes the save (`starters:1` puts the roster back to a first-run one, so the locked tiles and their hints can be shot from a save with developer mode on) — a fresh save has nothing reached and nothing claimed, so a shot of Season or Shop only ever showed the locked state, and the claimed, claimable and current-tier states are most of what those screens are; and `NS3_MENU_SWITCH=<screen>` + `NS3_MENU_SWITCH_AT=<sec>`, which navigate a SECOND time once the first screen has settled and shoot that many seconds into the hand-off — a transition between two screens lasts a quarter second and is otherwise unshootable, the same reason `NS3_END` and `NS3_KILL` exist, and it is where an outgoing screen and an incoming one can end up drawn on top of each other. It goes through the nav bar's own button where the target is a tab, so the harness takes a thumb's route rather than a copy of it: calling `pop_all()` + `show_screen()` by hand is NOT what the nav does and quietly reproduces nothing), `NS3_MODE=showdown|cup` (which mode to drop into; needs one of the menu-skipping hooks alongside it, and also works when `game.tscn` is run directly), `NS3_RESET_SAVE=1` (delete the save, start fresh), `NS3_SIM=<n>` (balance sim: n all-bot matches at 10x speed, per-kit win/placement/damage table to stdout, then quits — run with `--headless`; the table's `hits/atk` column should sit near a kit's projectile count, and anything near zero means shots aren't landing, which is a delivery bug rather than a balance one — see `CHARACTER_BUILDING.md`), `NS3_SIM_SPEED=<n>` (override the sim's 10x time scale; re-run at 2 to tell physics artifacts from real balance), `NS3_HAPTIC_LOG=1` (print every haptic tap as it fires, with its score, tier and the gap since the last one, plus the fraction of max health for damage — and the DROPPED taps with the reason, which is how you tell a throttle eating one from a hook that never ran; haptics cannot be felt on desktop at all, so this is the only way to know either; see `docs/feel.md`), `NS3_HAPTIC_AUDIO=1` (play every haptic score as a low tone burst — the shapes are rhythms and a rhythm survives being heard, so this is how a score is judged without an install per change), `NS3_HAPTIC_DEMO=<name>` (loop one entry from `Haptics.SCORES` roughly once a second, for tuning on the phone itself), `NS3_SFX_LOG=1` (print every match sound as it fires, with its distance from the listener — synthesized audio is easy to mis-hear as missing when it is only quiet, so this is how you tell "the hook never ran" from "turn it up"), `NS3_SAVE_LOG=1` (Nobles Cup: print every loose-ball pickup with the pace, the angle to the catcher's own goal and whether an opponent touched it last — how the results card's SAVES row is tuned, and how you tell "the rule never matched" from "the situation never arose"), `NS3_BALL_LOG=1` (Nobles Cup: every time the ball leaves a pair of hands, why, and how far it then ran before it stopped or was collected — both of the complaints this settled, "a knock sends the ball further than a kick" and "a tap does one of two different things", are claims about a DISTANCE, which is exactly what a screenshot cannot show and one match cannot average; it also quits at the whistle, since a Cup match can be decided in twenty seconds and the results card otherwise holds the process open for the other two minutes), `NS3_AUTOPLAY=1` (hand the player's own slot to a bot brain as well, so a Cup match run from the command line is a real 3v3 rather than a 2v3 against somebody standing on the kickoff spot), `NS3_BOT_LOG=1` (print every time a bot takes cover, settles into a bush, holds an ambush, flanks a target it is losing to, closes on one behind cover, or takes the inside line to herd one into the gas — terrain use is rare enough per bot to look absent when it is only occasional, so this is the same "did the rule match" instrument as `NS3_SAVE_LOG`; a run that prints `wanted cover and found none` in bulk means the scan is firing where no wall can help). NS3_KIT/NS3_AUTOFIRE/NS3_SIM skip the menu. Net hooks (beat the single-player hooks): `NS3_HOST=<n>` hosts and auto-starts once n players are in the room, `NS3_JOIN=<ip>` joins — two windowed instances with `NS3_JOIN=127.0.0.1` + `NS3_SHOTS` on each is the wifi-play test harness. `NS3_AUTOWALK` and `NS3_AUTOFIRE` are honoured on a client too (they used to live only in `_run_playing`, which a client never reaches), so the harness can drive a predicted fighter. Also `NS3_NET_LAG=<ms>` / `NS3_NET_JITTER=<ms>` / `NS3_NET_LOSS=<0-1>`, which fake a worse link than a LAN — applied on both sides (the host delays inbound inputs, the client delays inbound snapshots), so setting them on both instances is a full round trip, and a jittered packet that would land out of order is DROPPED rather than delivered late, which is what the ordered channel really does; `NS3_NET_STATS=1` prints snapshot bytes/s (and, on the host, what the unpacked form would have cost), the client's interpolation buffer depth, how many frames it had to extrapolate, and the prediction reconcile error in centimetres — the one number that says whether prediction is tracking; `NS3_NET_KILL=<sec>` (host) eliminates every REMOTE player that long after FIGHT!, since a client's own results card is otherwise only reachable when a bot happens to kill it; and `NS3_NET_REMATCH=1`, which on a client asks for a rematch as soon as its card goes up and on a host deals the next match once the room has asked — the rematch is a round trip between two instances and cannot be checked from one. `NS3_FAKE_IOS=1` forces `Net.broadcast_works()` false, which is how the iOS room layout gets shot from a desktop. **`NS3_MODE=cup` is honoured on the HOST of a wifi harness run** (`NS3_HOST=2 NS3_MODE=cup`), and deliberately only there — the mode reaching the client through the roster rather than through its own environment is exactly the thing being tested. **Beware zsh when writing a harness script**: it does not word-split an unquoted `$VAR`, so `ENV="A=1 B=2"; env $ENV cmd` sets A to `1 B=2` and never sets B at all. Use `${=VAR}`. These are the testing strategy — there are no unit tests.

## Arena screenshots

**Arena screenshots without playing a match:** `Godot --path godot --script res://tools/render_map.gd` (**not** `--headless` — the dummy driver writes empty PNGs). `NS3_MAP_KIND=overview` shoots the whole map on the match's own light rig, which is how you judge a floor or a pond all at once and is the frame the events screen's map thumbnails will want; `NS3_MAP_KIND=game` shoots through `Arena.MATCH_CAM_*`, the real match lens, pointed at `NS3_MAP_AT="col,row"`. Also `NS3_MAP=showdown|cup`, `NS3_MAP_OUT=<dir>`, `NS3_MAP_SIZE=<px>`.

## Does a fighter fit?

**Does a fighter FIT?** `NS3_MAP=showdown Tools/godot.sh --path godot --headless --script res://tools/fit_probe.gd` places a fighter's own capsule at every open tile and asks the physics server whether it overlaps. Because `Kits.TILE == 2 * Kits.FIGHTER_RADIUS`, a one-tile corridor is exactly as wide as a fighter and passability rests entirely on `Arena.TILE_COLLISION_SHRINK` — **and `NS3_SIM` is blind to it**, since bots path on the ASCII grid and route around gaps they cannot fit through, leaving the balance table looking healthy while a player wedges. Run it after touching `TILE`, `FIGHTER_RADIUS`, `TILE_COLLISION_SHRINK` or either map. It was validated by reintroducing the bug it was written for (849 of 2625 open tiles unfittable at shrink 1.0, zero at 0.75) — an instrument that cannot fail is worthless.


## Running Godot by hand

`Tools/godot.sh --path godot` is the way in, and it encodes everything below under a
lockfile keyed on the resolved project directory: it **refuses** (exit 75) rather than
clearing, never kills anything, and reclaims only a lock whose owner is provably dead.
`--wait <sec>` blocks instead of refusing, `--status` names the holder, and `--no-lock`
is the deliberate escape hatch for the wifi harness, which is two instances of one
project on purpose. Because the lock is per PROJECT, separate git worktrees do not block
each other — which is what makes parallel agents workable.

The rest of this is what the wrapper encodes, and is still worth knowing when debugging
by hand. **Run one Godot at a time on this project.** Two processes contend on the import
lock badly enough to look like a hang: an import that normally takes 1.2s sat for six
minutes alongside a second instance and finished in 1.9s once it had the project to
itself. If a run or an import stalls with no output, check for another `Godot` before
debugging anything else. Three things about doing that, each of which has already gone
wrong here:

- **Detect with `pgrep -x Godot`, then check each hit's `--path`.** `pgrep -x` matches the binary by exact process name, so unlike `ps -eo command | grep Godot` it never matches the *shell running your own script* (that form reports a held lock forever, including when the lock is free — and the `[G]rep` trick does not save you, it only excludes the grep itself). But `pgrep -x` alone over-matches in the other direction: **another Claude session running `NS3_SIM` on its own scratchpad copy** of the project is a Godot process that holds no lock of yours, and waiting on it stalls indefinitely. This has already cost one session several minutes of dead waiting. Filter the hits:
  ```sh
  ours() { for P in $(pgrep -x Godot); do ps -o args= -p $P 2>/dev/null \
      | grep -qE -- '--path (godot|\.)( |$)|NobleStars/godot' && return 0; done; return 1; }
  until ! ours; do sleep 2; done
  ```
- **Never kill a Godot you have not identified.** A human playing the game looks exactly like a stale agent process except for two tells: its parent is an interactive shell (`-zsh`), not a Claude bash wrapper, and it was launched with an absolute `--path /Users/…/NobleStars/godot`. Agents here use `--path godot` from the repo root or `--path .` from inside it. Killing the wrong one closes the game out from under the person playing it. Wait, or skip the run.
- **Kill the job, not the binary.** `pkill Godot` leaves the shell that launched it alive, and it will start the next Godot in its chain minutes later and retake the lock.
