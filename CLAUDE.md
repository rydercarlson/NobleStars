# Noble Stars

Brawl Stars–inspired top-down arena battler (Showdown mode: last fighter standing, shrinking gas ring, loot-box power cubes). The whole project is the 3D Godot 4 game in `godot/`.

There was a v1: a SpriteKit/Swift 2D game in `NobleStars/`, complete and kept working alongside this one for a while. **It was deleted** — it had no users, it was not being extended, and having two iOS apps both called "Noble Stars" installed side by side was actively confusing. It is in git history if it is ever wanted back. Nothing outside that history should reference `NobleStars/`, `project.yml`, `xcodegen` or `Tools/generate_sprites.swift`.

## Two people work here

**Ryder owns gameplay** — kits, characters, balance, match feel, controls, modes, multiplayer, arena. Every character design is his call; nobody builds a fighter without him. **Jackson owns menus and assets end to end** — `godot/scripts/menu/` as a developer *and* the art: he designs it, makes it, and implements it. **All on-device testing is Ryder's**, whoever wrote the code — the phone is his and `devicectl` installs from his machine, so a menu change is a loop through him rather than a handoff. `ROADMAP.md` holds the split, the phases and the open decisions.

## Godot 3D game (`godot/`)

Godot 4.7, everything built in code (the `.tscn` files are near-empty shells). Entry scene is `menu.tscn` (Brawl Stars–style lobby, see below); `game.tscn` is the match. Scripts live in `godot/scripts/`: `main.gd` is the match hub (mirrors v1's GameScene), plus `fighter.gd`, `arena.gd`, `bot_brain.gd`, `gas_ring.gd`, `kits.gd` (character data), `projectile.gd`/`lob.gd`, `virtual_joystick.gd` (`TouchStick`, all three sticks — `super_button.gd` was folded into it), `session.gd`, `loading_screen.gd` (autoload `Loading`, see **Match bookends**), and for Nobles Cup `cup_mode.gd` (`CupMode`, the rules) + `ball.gd` (`Ball`). Menu system (see **Menu** below): `menu.gd` (`MenuShell` — stage scaling, screen stack, toasts/popups/particles), `menu_stage.gd` (`MenuStage` — the full-stage 3D view: the fighter on the arena's own ground, fading to ink), `scripts/menu/` (the screens), `ui_kit.gd` (the old navy/gold StyleBox helpers, now only `room_screen.gd` uses them), `save_game.gd` (`SaveGame` statics → JSON at `user://save.json`: per-fighter trophies, coins, gems, unlocks, pass progress, settings; Showdown ranks 1–10 award +8,+6,+5,+4,+3,+1,0,0,−1,−2 trophies, `max(2, 22−2·rank)` coins and `max(40, 180−12·rank)` Nobles Pass tokens via `SaveGame.award_match`, called from `main.gd:_end_match`). **Stats come from `kits.gd`, never from `brawlers.json`** — the JSON carries copy, art ids and shop/pass/news config only.

Run it: **`Tools/godot.sh --path godot`** (add `--headless --import` after adding files — REQUIRED after new scripts too, or class members silently vanish at runtime). That wrapper is `/Applications/Godot.app/Contents/MacOS/Godot` under a lockfile keyed on the resolved project directory: it **refuses** (exit 75) rather than clearing, never kills anything, and reclaims only a lock whose owner is provably dead. `--wait <sec>` blocks instead of refusing, `--status` names the holder, and `--no-lock` is the deliberate escape hatch for the wifi harness, which is two instances of one project on purpose. Because the lock is per PROJECT, separate git worktrees do not block each other — which is what makes parallel agents workable. The rest of this paragraph is what the wrapper encodes and is still worth knowing when debugging by hand. **Run one Godot at a time on this project.** Two processes contend on the import lock badly enough to look like a hang: an import that normally takes 1.2s sat for six minutes alongside a second instance and finished in 1.9s once it had the project to itself. If a run or an import stalls with no output, check for another `Godot` before debugging anything else. Three things about doing that, each of which has already gone wrong here:

- **Detect with `pgrep -x Godot`, then check each hit's `--path`.** `pgrep -x` matches the binary by exact process name, so unlike `ps -eo command | grep Godot` it never matches the *shell running your own script* (that form reports a held lock forever, including when the lock is free — and the `[G]rep` trick does not save you, it only excludes the grep itself). But `pgrep -x` alone over-matches in the other direction: **another Claude session running `NS3_SIM` on its own scratchpad copy** of the project is a Godot process that holds no lock of yours, and waiting on it stalls indefinitely. This has already cost one session several minutes of dead waiting. Filter the hits:
  ```sh
  ours() { for P in $(pgrep -x Godot); do ps -o args= -p $P 2>/dev/null \
      | grep -qE -- '--path (godot|\.)( |$)|NobleStars/godot' && return 0; done; return 1; }
  until ! ours; do sleep 2; done
  ```
- **Never kill a Godot you have not identified.** A human playing the game looks exactly like a stale agent process except for two tells: its parent is an interactive shell (`-zsh`), not a Claude bash wrapper, and it was launched with an absolute `--path /Users/…/NobleStars/godot`. Agents here use `--path godot` from the repo root or `--path .` from inside it. Killing the wrong one closes the game out from under the person playing it. Wait, or skip the run.
- **Kill the job, not the binary.** `pkill Godot` leaves the shell that launched it alive, and it will start the next Godot in its chain minutes later and retake the lock.

**`--headless --import` is NOT a compile check.** It does not report GDScript parse errors — a `main.gd` that could not load at all imported silently, and the `SCRIPT ERROR: Parse Error` only appeared on running the game. This is a sharp edge precisely because the PostToolUse hook makes the import feel like one. To know a script actually parses, run the game. A **PostToolUse hook in `.claude/settings.json` now runs that reimport automatically** after any edit to a `godot/**/*.gd`, so the footgun is handled for Claude Code edits; you still need it by hand after adding assets outside the editor. `godot/.godot/` is gitignored, so a **fresh clone must import once** (~5s) before the project will open or run.

**Wifi multiplayer** (`net_play.gd` autoload `Net`, `room_screen.gd`, net section at the bottom of `main.gd`): host-authoritative LAN play over ENet (port 42537). The host runs the exact single-player sim (bots fill empty slots); clients send stick input + fire requests up as RPCs and render 30Hz snapshots plus reliable events (attacks, eliminations, loot boxes, cubes, wall breaks) — `authoritative` in main.gd gates every mutation so client-side projectiles stay visual-only. Rooms: lobby → WIFI → pick a mode, then host or join. **Both modes play over wifi** (see **Nobles Cup over wifi** below).

- **The ROSTER decides the whole match, and it is the only thing that does.** `_net_host_start` deals `{peer, kit, fname, team, spawn}` per slot plus the mode, sends it, and builds from the same array — mode, who is in it, what they wear, which side they are on, which tile they start on. Nothing downstream may roll its own dice, because two machines rolling separately is two different matches. The mode travels *in the `_net_start` RPC* rather than being read from `Session.mode`, so a client that reached the scene with a stale mode still builds the host's arena. Bots go through `lineup_kits`/`next_bot_name` like every other match — this was the last lineup in the game still doing `pick_random()` with "Nova 3" nameplates.

- **`_net_prestart_tick` deals the FIRST match only, and the `_match_seq > 0` guard is load-bearing.** `_start_from_roster` drops `_match_ready` while it rebuilds, and that tick runs on every frame the flag is down — so a rematch had the host deal a brand new match on the very next frame. Because the rebuild `await`s a frame partway through, the second pass ran its `fighters.clear()` and its `get_children()` sweep BEFORE the first pass had spawned anything, so the first pass's roster was neither freed nor cleared and both passes appended: **exactly twice the fighters**, reported off a phone as 12 in a 3v3 and ~20 in a Showdown. Rematches come from `_net_host_start`'s own callers (PLAY AGAIN, KEY_R, the auto-rematch timer), never from the handshake. The log line prints `N of M fighters` — the array against the roster — because that discrepancy is what the old line hid.
- **The snapshot is a packed `PackedByteArray`, not a Variant array** — a ten-byte header plus fifteen quantised bytes per LIVING fighter (position to the centimetre, facing to 1/256 turn, ammo to 1/32 pip, the burn clocks to 1/16 s). Measured 4.7 KB/s against 29 KB/s for the unpacked form, 6.2x; `NS3_NET_STATS=1` prints both every two seconds so the claim stays checkable. **Nothing is delta-encoded on purpose**: the stream is unreliable, so a field only sent when it changes is lost for good when that packet drops.
- **The COUNTDOWN rides the snapshot header, because a client cannot time it itself.** Its `phase_at` is stamped when IT finished building the match, which is later than the host by the network hop plus however long its own fighters took to load — seconds on a phone, where net play does not go through `Loading` and so gets no preloaded GLBs. So the client's countdown started late, ran behind the host's, and was then cut off mid-number when the host's PLAYING phase arrived. One byte of the host's elapsed time (1/16 s) fixes it, taken off the NEWEST packet rather than the delayed render instant — a countdown is a clock, and the number it reaches zero on is shared. `NET_HEADER_BYTES` is the base offset three places index from; changing it means changing all three.
- **Clients interpolate everyone else and predict themselves.** Other fighters are drawn at `NET_INTERP_DELAY` (85 ms) behind the host's own clock, between the two buffered snapshots bracketing that instant — the host stamps its `now` into each snapshot and the client min-filters the difference into `_host_offset`. A starved buffer extrapolates for at most `NET_EXTRAP_MAX` and then holds. The **discrete** half of a snapshot (health, ammo, gas, players-left) is applied at that same delayed instant so a hit flash lands on the frame the body is drawn where it was hit — except for your own fighter, which is drawn at `now` and takes its numbers immediately.
- **Your own fighter runs `Fighter.apply_movement` locally** and the host acks the last input seq it applied; `_reconcile` replays every unacked input from the authoritative position when they disagree by more than 5 cm, and snaps past 2.5 m. `_pred_pos` (simulation) and `_pred_error` (a decaying visual offset) are **kept apart** — feed the offset back into the sim and the next correction double-counts it and the client twitches on every packet. The host **buffers inputs and consumes one per physics tick** rather than applying the latest, so two arriving in one frame are both used. Measured at 160 ms RTT with 3% loss: reconcile error avg 0 cm, max 15 cm.
- **`unreliable_ordered` DISCARDS an overtaken packet**, so a client whose frame rate drops below 30 receives one snapshot per FRAME — the ordered channel collapses the rest. Measured 12-18/s against 30 sent while a match's models are still loading. That is what the interpolation buffer is covering, not a bug to chase.
- **A client learns some things as NUMBERS and others as EVENTS, and every piece of feedback has to be hooked to whichever one it is.** This is the general form of the bug that made the whole haptic layer silent in wifi play: `death`, `elimination`, `cube`, `super_ready` and `count_go` were all hooked into host-side paths — `deal_damage`, the pickup Area, `_run_playing`'s countdown branch — that a client never runs. The rule is: **anything in the snapshot is watched frame to frame in `_update_status` (health, ammo, super charge); anything that arrives as an RPC is fired from that RPC's own handler** (`_net_eliminate`, `_net_cube_gone`, `_apply_snapshot_state`'s countdown transition). Watching is preferred where both are possible, because one hook then serves the host and the client and cannot drift. Two traps inside it: `_net_eliminate` must zero the local health before `die()` — `die()` does not touch it and `fighter_bars` skips only a fighter that `is_dead()`, so a full bar hangs over the body through the whole pop-out — and it must blank `status_label`, which reads off `player` and otherwise freezes at full health behind a card that says DEFEATED. "Who killed me" travels as a ROSTER INDEX, never a name: every machine calls its own fighter "You" and two players can share a name.
- **Attacks are not predicted.** A client's shot goes up as `_net_fire` and appears only when `_net_attack` echoes back, so firing costs a full round trip visually.
- **The rematch flow**: only the host can deal a roster, so a client's results card carries REMATCH (sends `_net_rematch_request`, then reads "WAITING FOR THE HOST…") instead of PLAY AGAIN, and the host's card counts "N of M ready". The host's own death shows results while its sim keeps running for whoever is still alive. A host that leaves writes "THE HOST LEFT — BACK TO THE LOBBY" onto the client's card, because the card covers the `center_label` the old notice used.
- **A client's results table is the host's numbers**, pushed by `_net_push_stats` immediately before the `_net_eliminate` that raises the card (and to the last survivor before `_net_match_over`) — `deal_damage` returns early when `not authoritative`, so the client's own `Fighter.stats` are all zeros. Guard the send with `multiplayer.get_peers().has(peer)`: the commonest elimination is a player who LEFT, and `_on_net_peer_left` eliminates their fighter from inside the disconnect handler.
- **Getting in is a JOIN CODE, not an IP**, and the code is not looked up anywhere — there is no server, so the code IS the address, compressed. Three widths, told apart by LENGTH: **4 chars** for `192.168.a.b` (16 bits, every home router), **5** for `10.a.b.c` and `172.16-31.a.b`, **7** for any other IPv4 — the catch-all, so a host on a school or campus network that routes public addresses still has a code. The alphabet is base 32 with every misreadable character removed (no `0/O`, no `1/I/L`), which is what leaves exactly 32. `Net.resolve_target` still accepts a typed-out IP in the same field.
  - **The number is scrambled by an odd multiplier mod 32^width, and unscrambled by its modular inverse.** Two reasons, both load-bearing: addresses are small numbers, so without it a house on `192.168.1.x` gets codes that all begin `22` and it stops reading as a code; and spreading the address across the whole code space means **94% of mistyped 4-char codes decode to nothing** rather than dialling a stranger's machine (88% at 7 chars; 5-char is only 47%, because that width is nearly full). `_mulmod` splits the multiplicand in half because the 7-char width multiplies a 35-bit number by a 35-bit constant — 70 bits, which silently wraps a GDScript int and yields a code that does not decode back. **`tools/code_probe.gd` is the check**, and it must be run *in Godot* rather than modelled elsewhere for exactly that reason: exhaustive over all 65536 of `192.168.*`, random over everything else.
  - **Discovery is broadcast AND a unicast sweep.** Broadcast is one packet and is desktop-only: iOS needs Apple's multicast entitlement to send to `255.255.255.255`. The sweep is a unicast probe to each of the 254 addresses in the host's own /24, spread `SWEEP_PER_FRAME` at a time, every `SWEEP_INTERVAL` — unicast to a LAN neighbour needs only the Local Network permission, which `export_presets.cfg` already declares (`NSLocalNetworkUsageDescription`). It runs on desktop too, as one code path rather than an iOS branch, and it also finds hosts behind access points that drop broadcast. **It only covers a /24**: on a flat school `10.x.x.x` the host may be in another /24 and never appear, and walking a /16 would be 65534 probes and would read as a port scan. That is survivable *because the code needs no discovery at all* — which is why `room_screen.gd` puts the code field above the games list on every platform now, not just on iOS. Neither can beat client isolation, which is what school and guest wifi usually have on.
  - **The browse screen is TWO COLUMNS, and that is what makes the keypad usable.** It was one 560-wide strip down the middle of a stage over 2000 px wide on a landscape phone, so the keys came out about 4 mm across against Apple's 7 mm minimum tap target — reported from the device as "really hard to type in". Hosting and browsing went left, the code and its pad right, and the pad took nearly twice the width. Key size is derived from `RIGHT_W`, so widening the column is the whole fix; shrinking the font is not.
  - **The code is typed on the game's own 32-key pad, not a LineEdit.** iOS brings up a lowercase QWERTY, so every character arrived in a case the alphabet does not have and got flipped under the thumb as it was typed; the keyboard covered half the screen; and two thirds of its keys cannot appear in a code, including the four (`0 O 1 I L`) removed from the alphabet *because* people confuse them. A pad of exactly the legal characters makes case and invalid input impossible, and base 32 falls out as **eight columns by four rows** — digits on the top row, letters below — so the gaps where I and O should be are visible rather than a rule you have to be told. JOIN lights up only once the code decodes, which turns the decoder's rejection into something you see before pressing rather than an error after. A physical keyboard still works (`_unhandled_key_input`), filtered to the same alphabet.
  - **A busy discovery port fails SILENTLY and looks exactly like "iOS blocked it"** — the room hosts fine, the code still joins, and nothing on the wifi can see the game. It happens when a previous instance of this game did not shut down and still holds 42538. `host_game` now checks the `bind` and says so. It cost an hour of blaming the sweep. When discovery misbehaves, check `lsof -nP -iUDP:42538` before anything else.
  - **The two halves of discovery are instrumented separately** under `NS3_NET_STATS=1`: the host prints `discovery probe from <ip>` and a browser prints `found game at <ip>`, so a failure is pinned to the direction it failed in. The sweep is verified desktop-to-desktop with `NS3_FAKE_IOS=1` (broadcast off, so the sweep is the only mechanism left) — and it probes its OWN address rather than skipping it, which is what makes that one-machine test possible. Skipping self was pointless anyway: the room screen stops browsing the moment you are in a room, so a process can never discover its own game.
  - **The unicast sweep WORKS on iOS — confirmed on a real iPhone.** Broadcast to 255.255.255.255 needs Apple's multicast entitlement and is desktop-only, but unicast to a LAN neighbour needs only the Local Network permission the app already declares, and a phone finds a desktop host with it "very quickly". That is the whole reason a Bonjour plugin is not urgent: see todo.md, where it now buys only the cross-subnet-beyond-/22 case and nothing that MultipeerConnectivity would not buy better.
  - **The sweep WIDENS until something answers, because Godot cannot read a netmask.** `IP.get_local_interfaces()` does not expose one, so the first pass assumes a /24 and every pass that finds nothing widens a bit, to a floor of /22 (1022 addresses); a game answering snaps it back. This is not hypothetical tuning — the development Mac reports `netmask 0xfffffc00`, a **/22**, so it sits at 192.168.7.110 while a phone on the same network sits at 192.168.5.x, three /24s away. A /24-only sweep found nothing there and looked exactly like iOS blocking it, while the phone joined by code from the very address the sweep was never going to reach. **Check `ifconfig` for the real netmask before concluding anything about discovery.**
  - `Net.broadcast_works()` (was `discovery_works()`) is now only "can we broadcast". `NS3_FAKE_IOS=1` still forces its false branch so the iOS path can be shot from a desktop with `NS3_MENU_SCREEN=wifi`. `Net.last_ip` is still remembered across launches in `user://lan.cfg` and prefills the field as a code.
- **Nobles Cup over wifi** rides on the same machinery, with the mode-specific state in eleven extra bytes per snapshot (`NET_CUP_BYTES`, appended only in Cup, so Showdown pays nothing). See **Nobles Cup** below for the rules; what the wire adds is: carrier index, loose-ball x/z, both scores, the clock, the kickoff freeze remaining and a flags byte. Everything else is a reliable RPC.
- **The gas ring's inset rides as fixed point, not as whole tiles.** `GasRing.inset` is a float that eases between steps (see **The gas ring**), so a snapshot packs `inset * NET_INSET_SCALE` into its s16 and the client divides it back out. Rounding it to an int gives the client back exactly the two-tile teleport the ease exists to remove — the wall would jump on one screen and creep on the other. A client also never calls `GasRing.start()`: its ring is written purely from the stream, rather than additionally running the shrink schedule and the gas damage loop locally underneath it.

- **Five surfaces, down from thirteen.** Home, Roster, Season, Shop, Wifi, plus the settings/profile popups. Deleted outright: News, Club, Inbox, Matchmaking-as-a-screen, the roster grid's detail card, and the storefront half of Shop. They were furniture for a live-service game this is not.
- **Home is also the detail screen** (`home_screen.gd`). The left flank is the selected fighter's identity and stat column, the right is their attack/Super write-ups and record; the middle is the live fighter. **This is what stops the width being dead space** — a single figure centred on a 1920 stage leaves two empty thirds, which is exactly the gap Brawl Stars fills with icon columns, and filling them with the fighter's own data means the width carries content instead of navigation. It gets better as the stage widens on a phone. Because home shows the detail, `RosterScreen` is a plain picker that selects and returns (two taps to change fighter, down from five).
- **Stats print as figures, not tiers.** `MenuData._merge` emits both: `speed`/`range`/`reload` are the tiered labels ("Very Fast"), and `speed_value`/`range_value`/`reload_value` are the raw numbers the flank column prints. A word in a table of numerals breaks the column and says less. Range is in **tiles**, the unit the balance work is done in.
- **The stage is a painting, lit per fighter.** `MenuShell.STAGE_BACKDROP` is the icon pack's dark hall with a lit floor, scaled to cover the stage; `MenuStage` renders the fighter over it on a **transparent** viewport (no ground plane, no fog — the arena-floor set it used to draw is gone, and the fog constants with it are inert) with a 2D pool and two rings under his feet (`_build_floor_ring`, centred on `HomeScreen.FEET_Y`). **The light takes the kit colour**: `STAGE_TINT_SHADER` recolours the painting by its own luminance — the hall stays navy where it is dark, the floor becomes the kit colour where it is lit — and the rings and pool follow (`_light_stage`, called from `select_brawler`), so nine fighters get nine stages from one file. A kit may name its own painting with a `stage` key and gets it untinted. The fighter is framed to `MenuStage.FILL` (0.64) of the stage height about a fixed look point, which is why his feet land at a known `FEET_Y` with no per-image floor line — the framing chain the old JPEG needed (`FLOOR_FRAC`, `BRAWLER_VIEW`, `_place_brawler`) is still gone.
- **`MenuUI.hex()` takes a Color as well as a string.** game.json carries colours as `"#57c81e"`; `kits.gd` carries them as real `Color`s that `MenuData` passes straight through. Round-tripping one through `str()` yields `"(0.2, 0.88, 0.78, 1)"`, which is not a colour name — Godot logged an error per fighter and returned black, which is why the roster's team blocks came out unpainted.
- **Layout is in "stage pixels".** Screens are authored against a 1920×1080 stage; `MenuShell._fit_stage` scales it to the device and grows it to COVER the display — *wider* than 16:9 (a phone) it gains width (2017 px of it on an iPhone 15), *narrower* (a 16:10 MacBook in fullscreen) it gains height. Keeping the height at 1080 whatever the display was tried first: on the 16:10 screen the picture became a letterboxed band while the chrome, anchored to the display, sat in the bars above and below it, which read as a crop. Anything that must sit under the fighter's feet hangs off `HomeScreen.FEET_FRAC` (a proportion of the stage height), not a pixel row, because `MenuStage` frames him to the stage height. The iOS safe area is honoured by insetting the `chrome` node, **not** by shrinking the stage: see **Phone fit** below, where doing it the other way is written up as one of the two P0s.
- **Files.** `scripts/menu/`: `menu_data.gd` (JSON + `Kits` merge — copy from the JSON, live balance from `kits.gd`; a kit with no JSON entry is synthesised, though as of Nova's entry there is no longer one. The JSON's own `stats` block is read by nothing; the `loadout` dict `_merge` emits has no reader either, since the screen that drew it was the roster detail card the overhaul deleted), `menu_ui.gd` (the design system), `menu_screen.gd`/`menu_popup.gd` (screen + popup bases), `menu_audio.gd` (every SFX synthesized at runtime — no SFX files ship), `home_screen.gd`, `roster_screen.gd`, `season_screen.gd`, `shop_screen.gd`, `modes_screen.gd`, `menu_popups.gd` (settings + profile). Every route in is `MenuShell.show_screen(name)`, which keeps the old thirteen-screen names as aliases so a stale hook lands somewhere sensible.
- **A screen leaving `_stack` is NOT a screen that has left the glass**, and every piece of shell state that keys off the stack has to allow for the 0.24 s (`MenuShell.SCREEN_EXIT`) its exit animation still runs for. Both halves of the "the roster's names overlap" bug were this one mistake. `push_screen`'s guard against "two screens printed on top of each other" hides `_stack[-1]`, which a screen mid-exit is no longer — and the nav bar pops and pushes in a single press, so the outgoing screen was invisible to exactly the guard written for it; `_drop_closing()` now sweeps `screens_root` for any `MenuScreen` not in the stack and drops it (hiding as well as freeing, since `queue_free` lands at the end of the frame). And `_update_stage_dim` restored `home` and the 3D fighter at the TOP of the exit, so a screen dissolved across them — two titles, two currency readouts in the same corner, nine names over the flanks. Home comes back when the screen has actually gone, which makes the exit fade over the painted stage, matching what the entrance always did. It then needs its own fade (`HOME_FADE`) because it is no longer being uncovered, and `brawler_view` must fade with it — it is home's SIBLING, so home's `modulate` does not reach it.
- **Godot layout gotchas this menu hit.** `PanelContainer` stretches *every* child to fill it, so a card with overlays must be `MenuUI.card()` — a plain `Panel` — with `MenuUI.card_body()`. `set_anchors_and_offsets_preset(..., PRESET_MODE_MINSIZE)` reads a minimum size a node does not have until it is in the tree; use `MenuUI.pin()`. A `ScrollContainer` has no minimum height, so a popup built around one collapses to its title bar.
- **Unlocks are real.** `SaveGame.ensure_loaded` seeds only `MenuData.starting_brawlers()` (Nova); everyone else is locked, shows their `unlockHint` in place of their numbers on the roster row, and arrives through a named Trophy Road milestone or a Dawg Treat. **Leon, Anders, Hammy and Ayaan have no named unlock**: the road covers Sanjit, Tony, Kovacs and Henry, so those four are reachable only through a Treat. Settings → Developer mode unlocks everyone on the current save.
- **Season merges Trophy Road and the Pass** (`season_screen.gd`), because they answer the same question and differ only in whether they reset. Road entries are `{trophies, reward: {kind, amount|id}}` (the older flat `{trophies, kind, ...}` is still accepted by `_payload`); Pass claims are keyed `pass:<tier>:<free|premium>`. Kinds: `coins`, `gems`, `power_points`, `bling`, `dawg_treat`, `star_drop`, `skin`, `pin`, `brawler` (named, by `id`) and `brawler_drop` (random, rarity-weighted, no duplicates). Adding a kind means touching `_reward_name`, `_reward_icon`, `_claim` and `SaveGame.grant` together. Laid out to Jackson's 7 Sep mockup, and three things about it are load-bearing:
  - **A reward is a picture of itself.** The rails used to set every reward as words — "250 COINS" in the display face — on the argument that a word reads faster down a rail and ships no file. Twenty columns of words is a wall of text, and what is being scanned for is *which kind* of reward, which is what a glyph answers first. Glyphs come from `assets/menu/svg/` (`dawg_treat`, `crown`, `ticket` and `pin` were drawn for this); a fighter, a skin or a pin shows the roster's own portrait render in a tile of the kit's colour, never a second illustration of them.
  - **A claimable card IS the button** (`_reward_card` returns a `Button` in that state, a `PanelContainer` otherwise). A gold CLAIM button *inside* the card was the obvious build and does not fit: `MenuUI.button` carries 16px of content margin and the display face's line box is 1.64x its size, so a 20px CLAIM cannot be shorter than 65 — half the tile — and every claimable column grew taller than its neighbours and pushed the rail out of its block. `MenuUI.button` now takes a `pad`, but the fix here was to stop nesting a button at all: the tile is also the bigger tap target on a phone. The state line is a word in all three states — tick, padlock, or CLAIM.
  - **The heights add up to 816 stage pixels and are checked, not estimated.** Nothing on this screen scrolls vertically, so `HEADER_H + ROAD_H + PASS_H + 2 gaps` has to fit between the top bar and `MenuUI.NAV_H`; overshoot puts the Pass's premium lane under the nav. Anton's line box is ~1.64x its font size and Barlow's ~1.2x, which is why every hand-computed budget here came out short — print `get_global_rect()` for the blocks and the nav rather than adding up font sizes. On a stage taller than 16:9 the blocks and the cards take the slack (`_grow`), because parked at the bottom it reads as a band of nothing; a `ScrollContainer` only stretches its child on the disabled axis if the CHILD carries `SIZE_EXPAND`.
- **Shop is a sink, not a store.** The gem packs priced in dollars, the bundles and the row of tiles reading PURCHASED are gone; what is left is the loop that was already real — `award_match` grants coins, so power levels, Dawg Treats and the resource swaps are where they go. `_affordable_deals` filters `game.json` by currency rather than hardcoding a list, so a dollar-priced item added to the JSON simply will not appear. The Treat's odds are printed from the same `TREAT_TIERS` that `_roll_tier` runs on.
- **Wifi play** is the WIFI nav tab, which opens `room_screen.gd` inside a bare `MenuScreen` host. The room is still `ui_kit.gd`-styled inside — the one corner the overhaul did not touch — but its back button is the menu's square arrow, so the corner matches.
- **`godot/assets/menu/` went from 124 files to 34**, and then gained `profile/` (the nine pack icons) and `svg/menu.svg`. What remains is what is still referenced: three fonts, `portraits/` (used by the versus screen, the results card and the loading screen — *not* by the menu), `svg/`, `profile/`, `audio/` (two MP3s: lobby music and the battle track — the versus sting was a Brawl Stars rip and is deleted, so the versus screen is silent until a synthesized sting replaces it) and `background/loading_keyart.jpg`. `bg.png`, the `btn_*` chips, `icons/`, `cards/`, `treats/`, `decor/` and `pack/` were all deleted with the screens that used them.

**Nobles Cup** (`cup_mode.gd`, `ball.gd`, `Arena.PITCH_MAP`) — the Brawl Ball mode, 3v3, first to two goals or ahead when the 2:30 clock runs out. Menu id `nobles_cup` → engine mode `"cup"`; `NS3_MODE=cup` alongside `NS3_KIT` drops straight into one.

- **Everything mode-specific is in `cup_mode.gd`**, which main.gd calls at four points: `build_match`, `tick`, `on_death` and `frozen` (the last holds input through a kickoff and after the whistle). Showdown's match loop is otherwise untouched, and `cup == null` is the guard on every branch.
- **Teams are real.** `Fighter.team` is 0/1 (−1 = Showdown free-for-all, where `is_ally` is false for everyone). `deal_damage` and `nearest_visible_enemy` both check it, so friendly fire and friendly targeting are off everywhere at once. Team is worn as a coloured ground ring — it can't tint the body, because eight of nine kits wear a GLB whose materials are the character's. **That ring is now drawn in every mode**, sized to the collision radius, which is how Brawl Stars shows a hitbox ("the ring around their feet, not the Brawler themselves"); in Showdown, where there is no team, it takes the kit colour. Health bars go green for your side and red for theirs (`fighter_bars.gd`); Showdown keeps kit colours.
- **Death is a setback, not an exit.** `_eliminate` hands off to `CupMode.on_death`, which parks the fighter (`Fighter.knock_out`) and books a respawn three seconds later; `fighters` never shrinks, and everything that walks it already skipped `is_dead()`. Overtime is sudden death and books nothing.
- **You respawn inside your own goal**, not at the kickoff spot — a body in the mouth is where the mode's defending comes from. There is deliberately no goalkeeper bot; an early build had one and it was strictly worse than the wall. Kickoff spawns are on the middle third, two tiles apart, so the whole team is on screen at the start.
- **The pitch does the defending.** 21x33 tiles — Brawl Stars' own 3v3 size, now that a tile is a body-width — mirrored on both axes (every row is a palindrome — keep it that way). A solid seven-tile breakable wall sits three rows off each goal, covering the five-tile mouth completely, so nothing can be shot at the mouth from beyond it and the attack has to come round the outside. **The two spawn rows must straddle `row_count / 2`** (integer division, 16 on 33 rows): `arena.gd` assigns team by that test alone, so a pitch whose spawn rows both land one side of it puts both teams in one half. Overtime levels every breakable wall, that one included, which is what opens the goals up. Only the `=` goal frame survives. Both teams spawn on the middle third, so a kickoff is a race.
- **The ball is not a physics body.** It reflects off `Arena.blocks_movement` per axis, so bounces are exact and reproducible; a RigidBody3D would creep into wall seams and squeeze the posts. It is caught by anyone it rolls within `PICKUP_RADIUS` of, which is what makes interception work.
- **The carry is clamped off walls** (`Ball._carry_point`). A fighter's capsule is 0.65 m and the ball is held 0.85 m in front, so a carrier pressed against a wall held it *inside* that tile — and at chest height the top of the ball (1.67 m) clears `Arena.WALL_HEIGHT`, so it surfaced through the top and read as floating over the wall. The carry is walked in until the ball is clear; `kick()` launches from that same point, which is also what stopped a point-blank kick starting the ball inside a wall, where `_advance` reverses it on both axes every frame and it never gets out.
- **The carrier can't attack at all, only kick.** A normal kick spends an ammo bar and obeys the same attack cooldown as a shot, as it does in Brawl Ball, so the ball cannot be machine-gunned up the pitch and running dry is a real reason to hold on to it. It runs 7.8 m — **6 tiles, and a tile is a fighter, so six body-widths** — deliberately inside the 8.5-tile weapon range cap, so kicking the ball never outreaches shooting it: a kick is a pass, not a shot from anywhere. **This sentence described ~7 m for months while the code ran 15.3 m**, and nothing caught it because the Cup camera only ever showed two thirds of the pitch width; locking that camera on 7 Sep 2026 made the whole pitch visible and it was reported from play within one match as "way too far/fast". Retune the DISTANCE by moving `Ball.DRAG`'s multiplier against `KICK_SPEED`'s — both derive from `Kits.SPEED_NORMAL`, which cancels out of `kick_range()`, so the speed dial changes how long a kick takes and never how far it goes. Spending the Super on the ball is the **Super Shot**: `Ball.SUPER_KICK_MULT` doubles the launch speed, and because drag is constant that doubles the distance too (~16 m, 12.4 tiles), matching Brawl Ball's "shoots it further and faster, but uses up the Super". It costs the Super and no ammo, so it is also the carrier's out when the magazine is empty. While carrying, the Super never fires the kit's Super, and an uncharged one is swallowed rather than falling through to an attack. Every player attack funnels through `main.gd:_fire_player`, which is the backstop; `_release_fire`/`_auto_aim_fire` resolve the aim first (drag aims, tap uses `CupMode.kick_aim`, which shoots inside `SHOT_RANGE` — doubled for a Super Shot — and otherwise passes). The aim indicator switches to the ball's own path, bounces and all, via `_aim_bounce_segments(..., decay)`; the Super Shot's lane is gold and twice as long.
- **The ball is dropped by a dash, a leap, or a knock that came from a SUPER**, on top of death. Brawl Ball's own rule is stun/knockback/defeat; dashes and jump-smashes are added because otherwise every mobility Super is a free run at the goal. **"From a Super" is a comparison, not a threshold, and that is load-bearing**: this used to be a bare speed test on `knockback_vel`, and Kovacs' clap shoves at 4.0 — over `KNOCK_DROP_SPEED` — so a *basic attack* on a normal reload stripped the carrier every time it landed. No constant can fix that, because Sanjit's **Super** also shoves at exactly 4.0. So `deal_damage` records the attacker on the target (`Fighter.knock_from`/`knock_strength`/`knock_dir`) and `CupMode._knock_was_super` asks whether the impulse beat that attacker's OWN `weapon.knockback`. Every kit gives its Super more knockback than its attack, so this stays correct for a kit added later with nothing retuned. The ball keeps a capped share of the shove (`Ball.knock_loose`, `KNOCK_BALL_MAX` ≈ 6 m against a kick's 15) so a strip reads as knocked away without ever becoming a shot; `last_touch` is deliberately unchanged, since whoever landed the Super never touched the ball. `Fighter.forget_knock()` spends the shove the instant it takes the ball — a 10 m/s knock decays over ~0.58s against a 0.35s pickup hold, so without it the carrier re-collected while still wearing a live knock record and was stripped three times off one Super.
- **A Cup tap tells you which of its two jobs it is about to do.** `CupMode.kick_plan` returns `{kind, at, dir}` with kind `shot` / `pass` / `clear`, and `main.gd` draws a ring on `at` — the goal, or the team-mate. The rule was never wrong; the tell was missing, so a tap silently did one of two very different things depending on a distance the player could not see. `kick_aim` remains the direction-only half for callers that just kick, and the bots read the same plan, so the ring and the tap cannot drift apart.
- **Bots route around the goal wall** rather than into it. `Arena.route_to_goal` is a BFS distance field per goal, rebuilt only when a wall opens, with a five-tile lookahead so the run is a curve and not a corner-hug. Steering straight at the mouth parked carriers against the wall until someone took the ball off them; measured after the fix, carriers deviate >40° from the straight line exactly at 6-9 m out, which is where the wall is.
- **A destroyed wall leaves the ASCII map** via `Arena.open_at`, called from the projectile hit, the net RPC and overtime. Bot movement, route finding and the ball's bounces all read `Arena.rows`, so a wall only freed from the scene keeps blocking every one of them — overtime would otherwise leave the ball rebounding off gaps you can see through. This applies to Showdown too, where bots previously kept pathing around walls that were no longer there.
- **Pacing lives in four constants.** `Ball.KICK_SPEED`/`DRAG`, `Ball.SUPER_KICK_MULT`, `CupMode.SHOT_RANGE`, and the goal wall. Retune those before touching anything else, and re-measure with a batch of headless matches rather than one — variance between single matches is large. All three ball constants **derive from `Kits.SPEED_NORMAL`**, which cancels out of `kick_range()`: the game's speed dial changes how long a kick takes and never how far it goes. Retune the DISTANCE with `DRAG` against `KICK_SPEED`, and the PACE with `STOP_SPEED`.
- **THE TEST FOR THE BALL IS WHETHER IT BEATS A RUNNER**, not how fast it leaves the boot — `dist / time` against `Kits.SPEED_NORMAL`. For the whole life of the project it did not: every tuning ever shipped averaged **0.62-0.76x a fighter's run** over the length of a kick, because exponential decay spends most of its time in the tail, so the ball launched fast and then trickled and a defender could jog after any pass. It was reported as "kick still too slow" only after the launch speed had been cut twice for it — **the launch was never the problem.** `Ball.STOP_SPEED` was: ending the roll at 0.42x a run instead of 0.11x cuts the tail, and the same 8-tile kick lands in 2.0 s instead of 4.6, averaging 1.45x a run. The old "a fast ball made every shot a goal and ran a match out in thirteen seconds" is still true of the LAUNCH speed and is why it is 3.5x a run rather than more.
- **A tapped kick locks onto the GOAL and nothing else.** It used to hunt for the team-mate nearest the goal, which is a lock-on: it picks a receiver for you and the ball leaves in a direction you cannot read off your own facing — the same objection recorded against the attack indicator previewing auto-aim's pick. In range of the goal it aims at the goal; otherwise it goes where you are facing. `CupMode.kick_plan`'s `allow_pass` is false for the player and **true for bots**, which need it: a bot has no drag to fall back on and a 3v3 where nobody passes is not the mode. The indicator marks where the ball STOPS ROLLING, drawn always, and that ring is deliberately smaller than the goal ring — one is a distance read-out, the other is a target, and they must not read alike.
- **The Cup camera is pulled back AND LOCKED HORIZONTALLY** (`Arena.CUP_CAM_PULLBACK`, `Arena.cam_anchor`). Brawl Ball never scrolls sideways; both touchlines are always visible. **Pulling back alone is not enough** — a wider window that still follows the player in X loses a touchline just the same, only more slowly. Two traps: the camera's position and its `look_at` target must come from the SAME anchor, or it yaws to face an off-centre player and — since rotation is fixed at match start — renders the whole pitch visibly TILTED for the entire match; and the framing hid a real balance bug for months, because a camera showing two thirds of the pitch is a camera you cannot check a kick's range against.
- **The goal is a net on the floor plus a real frame.** `Arena._build_goal` derives everything from `goal_mouths` — never from PITCH_MAP row numbers — so a wider mouth or a second pitch gets its goal for free. The mouth floor is a team-tinted grid that darkens toward the back, and that gradient is the whole depth cue: the recess is one tile deep and the camera is nearly overhead, so there is no other way to see into it. Posts and crossbar stand on the goal line at `GOAL_FRAME_HEIGHT`, deliberately taller than `WALL_HEIGHT` — a bar level with the wall behind it disappears into it at this pitch.
- **Wifi play: the host runs the rules, a client's CupMode is a presentation layer.** `CupMode.authoritative` mirrors main.gd's, and `tick()` branches on it into `_client_tick` before any rule runs — no pickups, no goal test, no carrier check, no clock, no respawns. Same split `GasRing` already uses, where a client builds the node and never calls `start()`.
  - **State rides the snapshot; EVENTS ride reliable RPCs.** The score, clock, freeze, overtime/finished flags, the carrier's roster index and a loose ball's position are state. A goal, a knock-out, a respawn, a kickoff and a kick are events — each happens once and is unrecoverable from a later packet, exactly like Showdown's elimination feed. `CupMode.goal_effects` is the presentation half of `_goal_check`, split out so the host and a client run the *same* code and cannot drift.
  - **The carrier rides as an INDEX, not as the ball's position.** A client then draws the ball through its own `Ball._carry_point`, which is what makes the ball track its own *predicted* fighter with no round trip when the client is carrying. A LOOSE ball is interpolated in `_net_render_puppets` like a puppet, not applied in `_apply_snapshot_state` — a Super Shot leaves at 28 m/s, nearly a metre between snapshots, so taking it off the newest packet shows as a ball stepping across the grass.
  - **A client's own PICKUP is applied off the newest packet, not the delayed one.** Everything else about the ball can afford `NET_INTERP_DELAY`, because everything else about it is something you are watching; running onto a loose ball is the thing you are *doing*, and 85 ms on top of the round trip before it sticks to your hands is most of what made the mode feel remote. `CupMode.apply_local_carry` owns the local case entirely and `apply_net_state` returns early for it — otherwise an older packet walks the pickup straight back and the ball sticks, then comes loose a frame later. Same rule the client's own health and ammo already follow.
  - **The host must not drive a remote player through a kickoff freeze.** `_run_playing`'s `if net_host` block was the only one of the three movement blocks not gated on `held`: the freeze zeroes everyone's movement at the top of the function, and this then put the remote player's LAST input back on top, because `_consume_input` returns the previous input when the queue is empty and a frozen client has stopped sending. Their fighter crept across the pitch on the host while standing still on their own screen, and the freeze lifting brought it back as a correction. Measured 2-3 cm average prediction error with 29 cm spikes in Cup against a flat 0 in Showdown, which has no freeze for it to happen in; flat 0 in both after the gate.
  - **A client kicks by ASKING.** `_fire_player`'s "am I a client" test now comes *before* the `cup.kick` backstop — with it after, a client moved the ball on its own screen and never told anybody. The host runs the identical `cup.kick` inside `_net_fire`, and echoes `_net_cup_kick` only when the ball actually left the carrier's hands (which it tests by `ball.carrier != f`, since `kick()` also returns true when it swallowed the input for want of ammo). Aiming stays local: `kick_plan` is pure geometry over data the client already has.
  - **Anything that teleports the client's own fighter must call `_net_resync_prediction()`.** `_net_predict` starts each frame with `player.position = _pred_pos`, so a kickoff or a respawn that moved the body without moving the prediction is undone on the first unfrozen frame — the fighter snaps back to where it died, holds for a round trip, then gets dragged forward. It reads as the respawn not working. The client also skips prediction entirely while `cup.frozen(now)`.
  - **`CupMode._kick_spot` is per-fighter, replacing the two `_lineup` arrays.** build_match and kickoff used to walk those with separate counters, and when the counters disagreed two fighters landed on one tile and the depenetration fired them hundreds of metres up. Storing the answer per fighter instead of the recipe for computing it twice makes that impossible, and it is what lets a client agree with the host — the host simply sends each fighter's spawn index in the roster.
  - **The results board is DATA, not six live fighters.** `_cup_rows()` builds `{name, kit, team, goals, kills, damage, idx, you}` and the host broadcasts it in `_net_cup_over`; a client's own `Fighter.stats` are all zeros. Two traps it already hit: the name must come off the **roster**, never `display_name`, because every machine calls its own fighter "You" and a broadcast table otherwise gives everyone a team-mate literally called YOU; and the "YOUR TEAM" column is `player.team`, not team 0, because over wifi you may well be on team 1.
  - **A player who leaves is handed to a bot brain** rather than eliminated. Showdown can afford to remove them; a 3v3 cannot, and their side would play the rest of the match two-against-three.
  - Room capacity is `Net.room_capacity()` — six in Cup, ten in Showdown — and the host picks the mode in `room_screen.gd` before pressing HOST. Humans fill one side before the other, the way a party does in Brawl Stars.

**Bushes** (`arena.gd`, the block under `GRASS_MODEL`): each `b` tile gets two MultiMesh instances — a flat **skirt** quad sized exactly to `Kits.TILE` and a `tall_grass.glb` **canopy** on top. The skirt is what makes a bush read as a *tile*: adjacent quads meet with no seam, so a patch becomes one contiguous dark shape, and its outline is merge-aware (`_open_edges` packs "this side has no bush neighbour" into `INSTANCE_CUSTOM`; the shader rims only those sides, so a 3x3 patch is one shape and not nine squares). The canopy has no yaw/scale jitter on purpose — the old jitter existed to stop a field reading as tiled, which is now exactly the goal. Both layers fade any instance within `Kits.BUSH_REVEAL` of `reveal_center`, which `main.gd:_update_concealment` points at the player every physics frame, so the concealment radius `can_see()` enforces is the same one you can see through. Two gotchas: both layers are transparent and never get a depth sort, which works only because `_build` appends bushes row-major from the map's -Z edge (the far side of a camera at +Z) — that buffer order *is* the painter's order; and the skirt carries `render_priority = -1` so it never flips in front of its own canopy.

**Terrain** (`arena.gd`, the "terrain look" block) — the floor, the walls and the water are three fragment shaders over flat colour, no art files, for the same reason the sounds are synthesized: a fixed steep camera only ever shows one angle.

- **Shadows were switched on and drew nothing for the life of the project.** The match camera sits 105.5 m back behind a 7° lens, so the whole arena is further away than a directional light's **100 m default `directional_shadow_max_distance`** — correct shadows, entirely outside the volume they get drawn in. `Arena.make_sun()` sets 145 m with one orthogonal split. Anything that renders the arena has to use `Arena.make_sun()` / `make_environment()`; a second copy of those numbers is how the tool and the game drift apart.
- **Walls and water share the bushes' merge-aware outline.** Each tile's "which of my four sides has no neighbour" mask rides an **`instance uniform`** (`open_edges`), so all ~400 walls share one material and one shader and still each get their own rim — and `open_at` hands the four neighbours of a hole a fresh mask, so a wall shot out re-outlines what is left. `_open_sides` treats off-map as matching, so the border ring is not outlined against the void.
- **Water is opaque now.** The old translucent slabs blended against the floor *and* against each other, so a pond showed a grid of seams where its tiles overlapped. Foam width is the constant to watch: a single-tile pond is only 2 m across, and the first pass at 24% of a tile per side left almost no water in the middle of one.
- **A tile-scale checker cannot be the floor's variation.** However faint it is made it reads as a chessboard; two octaves of value noise at 18 m and 6 m read as ground. The checker is still there at ~2%, under the noise.
- **The arena sits on a slab inside a surround plane.** Past the map edge used to be raw sky. `SURROUND_HORIZON` is also `Environment.background_color`, so the scenery meets the background with no seam — change one and change the other.
- **Nobles Cup's pitch markings are painted by the floor shader** (`pitch_mark`, from `_playable_rect()`), not laid down as geometry, so a line costs nothing and cannot z-fight the grass. Showdown passes `pitch_lines = 0`.
- **Wall height is purely visual** — `Lob` is a `Node3D` with no collision and arcs over walls logically, `begin_leap` sweeps terrain itself, and both the LOS ray (y = 1) and every projectile (y = 1) already sit inside a 1.5 m box. `Arena.WALL_HEIGHT` can be retuned on looks alone.

**The gas ring** (`gas_ring.gd`) — Showdown's shrinking safe zone, and the same shaders-over-art-files rule as the terrain.

- **`inset` is a FLOAT and everything reads the eased value, the rules included.** It steps on exactly the old cadence (`FIRST_SHRINK_DELAY` 18 s, then `TILES_PER_SHRINK` 3 every `SHRINK_INTERVAL` 12 s) but takes `SHRINK_EASE` = 3 s to travel each step instead of teleporting. Easing only the *visuals* was the alternative and it is a lie the player cannot see through — for the whole ease you would burn on ground that reads as safe. Everything outside the file already went through `contains()` / `depth_inside()` / `safe_min()` / `safe_max()` / `safe_center()`, all floats, so bots' `gas_depth` steering got a continuously moving edge for nothing.
- **The rate is what to check when retuning, not the duration.** A smoothstep peaks at 1.5x its average: 3.9 m in 3 s tops out at 1.95 m/s against `Kits.SPEED_VERY_SLOW`. The wall must stay walkable-out-of. **`TILES_PER_SHRINK` is in TILES, so it had to go 2 → 3 when the tile shrank** — at 2 the ring needed 15 steps instead of 10 on the 61-tile map and full closure went from 126 s to 186 s, which also lengthens every `NS3_SIM` match by half.
- **The cloud bank is parametric, not reseeded.** Every instance stores its edge, its position along it and its own jitter/scale/yaw, generated once at a constant seed; world transforms are recomputed from the eased edge every frame. The old code did `rng.seed = 7 + inset` and rebuilt, so the whole pattern popped on every step. The count per edge is fixed and the clouds *bunch* as the ring closes rather than being culled — culling puts the pop back, and dropping instances from the buffer breaks the only thing that sorts a MultiMesh of transparent instances, which is the order they were written in (far edge, flanks, near edge = back-to-front at +Z). The MultiMesh needs `PHYSICS_INTERPOLATION_MODE_OFF` because it is driven from `_process`.
- **A translucent fill loses to grass, and that is a LINEAR-space fact.** The old four `BoxMesh`es at 22% read as a purple filter over the picture, not as gas: blending happens in linear, where grass's green channel is 0.45 against a dark violet's 0.003, so any plausible-looking violet composites to a dead grey-green. The fill is one shader over two quads now (a mat at ankle height, a haze at 2.6 m drifting faster, so the pair separates under the camera pitch), and it is **nearly opaque with almost no green** — at 0.93 alpha `ALBEDO` is more or less the answer. It can afford that because the mat is under a fighter's feet and never occludes anyone; only the thin haze is ever between the camera and a body.
- The front is the safe rectangle's box SDF pushed about by a noise octave — that is what stops it reading as a rectangle. Both quads carry a `rim_fade` so they end before their own straight edge does (the haze is 2.6 m up, so its rectangle projects clear of the arena slab's lip and was the most obviously wrong line on screen).
- **`gas_cloud.glb` is preloaded in `Loading.to_match`** (Showdown only), because the bank is now built on the match's first frame rather than at the first shrink — the same trap as `power_cube.glb`.

**Haptics** (`haptics.gd`, static class `Haptics`) — the phone's half of the feedback layer, and the third thing after the SFX and the VFX that ships no asset file.

- **Godot's iOS backend emits ONE event type and ONE parameter, and everything here follows from that.** `Input.vibrate_handheld` reaches `AppleEmbedded::vibrate_haptic_engine` (`drivers/apple_embedded/apple_embedded.mm`), which builds a Core Haptics pattern holding a single `CHHapticEventTypeHapticContinuous` with only `HapticIntensity` set — never `CHHapticEventTypeHapticTransient`, never `HapticSharpness`. So the engine can express duration and strength and nothing else. A table of duration/amplitude pairs is therefore N lengths of ONE sensation, which is why the first pass read as undifferentiated: a menu tap and a goal had the same texture because there is only one texture. Getting a real click or a timbre axis needs a native plugin, which is written up in todo.md.
- **The missing axis is bought back as RHYTHM.** Core Haptics mixes concurrent players and GDScript can schedule calls, so a tap is a SCORE — `[[offset ms, duration ms, amplitude], ...]` — with the head fired on the frame and the tail queued. A hard 20 ms segment followed by a soft 60 ms one reads as an impact where one 80 ms block reads as a hum; a goal is three rising thumps. Every shape in `SCORES` is built out of that one idea. The queue drains in `_process`, so segments carry a frame of jitter (measured over a Cup match: 0-8 ms, median 4; a 60 fps phone tops out around 16) — which is why **nothing places two segments closer than ~40 ms**.
- **Three device classes, probed, not assumed.** `OS.has_feature("mobile")` is also true on an iPad, which has no haptic engine at all, so `_device()` asks the platform singleton — `AppleEmbedded` (or `iOS` on older templates) binds `supports_haptic_engine()` into ClassDB. TAPTIC gets the scores; BUZZ collapses every score to its loudest segment and drops any that peaks under `BUZZ_MIN_AMP`, because `AudioServicesPlaySystemSound` ignores both arguments and answers everything with the same ~0.4s buzz — a `ui_tap` would arrive as a 0.4s buzz on every menu press. **That fallback is a real constraint that this build never meets**, since it side-loads onto a modern iPhone, and designing the whole vocabulary around it was the first pass's other mistake.
- **Tiers, not just spacing.** The old throttle was first-come-first-served inside `MIN_GAP`, so a menu tap could swallow a death — the killing blow fires `hit` from the health watch and `death` from `_eliminate` in the same frame, and which survived depended on frame ordering. Every entry now carries a `Tier` (PICKUP / EVENT / CEREMONY / MATCH) and a higher tier preempts a lower one, clearing whatever it had queued. **The axis is what happened in the match, not what it cost you**: firing your Super is an EVENT and the elimination it produced is a CEREMONY, which is load-bearing — ranked the other way the kill was measurably eaten, since a Super that kills lands both inside 160 ms.
- **`Haptics.warm()` at match start and on entering the menu.** Godot builds the engine with `setAutoShutdownEnabled:true`, so it idles down between taps and the first one after a lull pays the start-up cost — and a Showdown lull is easily ten seconds, which makes the late tap exactly the one that mattered. The queue needs a frame signal, so a single hidden `Pump` node is parked on the scene ROOT (surviving the match/menu swap without having to become an autoload and rename every call site); it also stops the engine on `NOTIFICATION_APPLICATION_PAUSED`.
- **The damage curve is measured and was re-measured.** `HIT_SOFT`/`HIT_HARD` (0.06–0.34) replace the old single `HEAVY_FRACTION` threshold: damage dealt runs 8-28% of the target's max with a median of 14%, a gas tick is a flat 17%, and a shot lands for 9-29% by kit and range — so essentially everything lives between 6% and a third. A first pass at 0.05–0.45 spent over half the amplitude range on damage that never occurs and put every real hit between 0.36 and 0.61 of a scale running to 0.98. Re-measure with `NS3_HAPTIC_LOG` before touching these.
- **Damage taken is watched in `main.gd:_update_status`, not hooked into `deal_damage`.** A wifi client never runs `deal_damage` at all (`authoritative` returns it early) and takes its health off the snapshot stream, so reading the number frame to frame is the one hook that covers both — and a nine-pellet shotgun arrives as one exchange.
- **Damage DEALT is banked over `LANDED_WINDOW`, not a frame.** A shotgun's pellets are nine projectiles with their own flight times, so they land across three or four frames: banking per frame still collapsed to one tap (the repeat gap), but that tap carried the first frame's share and read as a third of the blow it was. `landed` is deliberately a different RHYTHM from `hit` — two even ticks against a thump-and-tail — and capped well below it, because what happens TO you must always outweigh what you do to someone else.
- **The aim stick has a detent** (`main.gd:_update_aim_detent`): `aim_on`/`aim_off` fire as `value` crosses `TAP_THRESHOLD`, which is where the stick stops meaning "tap to auto-aim" and starts meaning "this is the lane". The indicator does change with it, but the indicator is under your thumb while your eyes are on the fight. Two details are load-bearing. It is watched **per frame, not off `_unhandled_input`** — a drag event only arrives while the finger is MOVING, so a thumb that crosses the line and holds still stops generating them. And the anti-chatter is a **dwell, not hysteresis**: a hysteresis band would make the tap claim a state the game is not in for the width of the band, whereas a dwell only declines to report a crossing that did not last. A release resets the state silently, since the shot that follows has its own feedback.
- **Only ever your own events.** Every hook is gated on the local player — a bot dying across the map is a sound, not something your hand should know about.
- **`REPEAT_GAP` sits on top of `MIN_GAP` for taps that arrive as a stream.** A gas burn ticks about twice a second, a sustained magazine lands two to five connects a second, and held fire on a dry magazine clicks 2.4 times a second — that last one is fine to hear and a rattle to feel, so `empty` is gated at 1.2 s (four times the sound's own gate) and pairs with `ammo_ready`, which fires only on the pip that takes you from empty back to able to shoot rather than on every pip.
- **Three instruments, because none of this can be felt on a desktop.** `NS3_HAPTIC_LOG=1` prints every tap with its score, tier and gap — and prints the DROPS with their reason, which is how you tell a throttle from a missing hook. `NS3_HAPTIC_AUDIO=1` renders each score as a low tone burst through a plain `AudioStreamPlayer`: rhythm is the thing being designed and it survives the translation to sound, so shapes can be compared without a device install each time. `NS3_HAPTIC_DEMO=<name>` loops one entry, for tuning on the phone itself.
- Toggled by `SaveGame.haptics_on` (Settings, beside Music and SFX). The row shows on desktop as well, where it can do nothing: the save travels to the phone with the build and that is the only place it can be set.
- **The menu's entire haptics is one line in `MenuUI.press_feedback`**, which every pressable already goes through, plus `MenuShell.HAPTIC_SOUNDS` for the handful of grant sounds a press does not cover.

**Match bookends** (`loading_screen.gd` autoload `Loading`, `versus_screen.gd`, and the results half of `main.gd`) — what wraps a match at both ends.

- **Entering and leaving a match go through `Loading`,** never `change_scene_to_file` directly. It is an autoload precisely so it outlives the swap it is covering: a loading screen owned by the scene being replaced dies halfway through the job. `Loading.to_match(get_tree())` (from `menu.gd:start_match`) and `Loading.to_menu(get_tree())` (LOBBY, and a lost host) threaded-load the target scene **plus every character GLB**, keep a reference to each in `_held` for the life of the session — which is what makes `fighter.gd`'s later `load(kit.model)` a cache hit instead of a disk read on the frame a fighter spawns — and only lift once the incoming scene calls `Loading.done()`. That call is at the **end of `start_match()`**, not in `_ready`: `start_match` awaits a frame partway through, so `_ready` returns before the arena exists. `MIN_SHOW` keeps the screen up long enough to read as a transition rather than a flash, and `SAFETY_SECONDS` lifts it anyway if a path forgets to call `done()`. The `NS3_*` hooks that skip the menu deliberately keep the old direct scene change, so the sim and screenshot harnesses are untouched.
- **The engine's boot splash is a PNG of this screen's first frame**, not a second design. `LoadingScreen.compose()` builds the screen as a detached Control tree — `_build` calls it, and so does `tools/make_boot_splash.gd`, which shoots it to `assets/menu/background/boot_splash.png` for `application/boot_splash/*` in project.godot. **Re-run the tool after changing the loading screen** (`Godot --path godot --script res://tools/make_boot_splash.gd`, *not* `--headless`), or boot and every transition after it stop matching. Coupled facts: `boot_splash/bg_color` is `LoadingScreen.BASE_INK` by hand, because 4.7's `stretch_mode` defaults to **Keep**, which fits the image and paints that colour into the columns either side on a phone (Cover would crop 11% off the bottom of a 19.5:9 screen, which is where the title and bar are anchored); the render composes at the authored 1280x720 and shoots at 1920 through `size_2d_override`, so the type rasterizes at the larger size instead of being an upscaled bitmap; and the PNG is imported `keep` **and** named in `export_presets.cfg`'s `exclude_filter`, because the exporter adds the boot splash by path on top of the resource sweep and it otherwise ships twice (40.0 MB → 37.2 MB). The iOS launch storyboard falls back to the same two settings, so it comes along for free on the next export.
- **`ResourceLoader.load_threaded_get` CONSUMES the request.** Poll a path again after collecting it and `load_threaded_get_status` reports `THREAD_LOAD_INVALID_RESOURCE` — so a naive "re-check everything each frame" loop sees every *finished* load as a *failed* one. Collect each path once and drop it from the pending list.
- **Per-match stats are on the fighter** (`Fighter.stats`: damage, kills, cubes, goals, saves, survived). Always on, and distinct from `main.gd`'s `sim_stats`, which is a per-KIT aggregate gated behind `sim_active` and answers a different question. Nothing in `stats` is cleared by `respawn()` — a Nobles Cup death is a setback inside one match, so a carrier who scores and then dies keeps the goal. `survived` measures from `match_start` (set when the phase turns PLAYING), not from `now`, which runs for the life of the scene and would otherwise report the second match after PLAY AGAIN as the sum of both.
- **All three ways a match can end funnel through `main.gd:_show_results`** — Showdown placement, a Cup scoreline, and a net client whose own fighter went down while the host's match ran on — so they cannot drift apart. It builds a `MenuUI` card fresh each time into `results_body`; only the overlay root and its dim persist. Its optional `board` argument swaps the portrait-plus-stat-table body for a prebuilt one: Cup passes `_cup_scoreboard` (both teams, all six players, sorted goals-then-damage), Showdown and the net client pass nothing. Two details are load-bearing — `hud.move_child(results, -1)`, because the fighter health bars are added to the HUD *after* the overlay is built in `_ready`; and hiding `CupMode.HUD_GROUP`, because Cup's scoreboard sits on its own layer *above* the card, where `move_child` cannot reach it and the scoreline printed twice. Hidden rather than freed — `CupMode._build_hud` sweeps it on PLAY AGAIN.
- **A per-player table is possible in Cup and not in Showdown.** `game.fighters` never shrinks in Cup — a death parks a fighter rather than freeing it — so everyone is still there at the whistle with their stats intact. Showdown frees them on elimination, so by the results screen most of the roster is gone.
- **A net client's stat table is the HOST's numbers.** Every mutation is host-side (`deal_damage` returns early when `not authoritative`), so a client's own `stats` are all zeros; the host pushes the real damage / eliminations / cubes / survival with `_net_push_stats` just before the elimination that raises the card, and `_net_rows` prints those. The one-row survival-clock fallback is still there for when they have not arrived.
- **`MenuUI.stagger` must not be used on rows in a container.** It goes through `pop_in`, which tweens `position:y`, and a `VBoxContainer` OWNS its children's positions: `pop_in` reads `home` off a child the container has not laid out yet, records 0 for every row, and animates the whole table into one stack where only the last row drawn is visible. The card then looks like it has one row while the code says four. `main.gd:_fade_in_rows` is the results table's own stagger and fades alpha only.
- **The versus screen already animates** (cards slide and stagger, VS punches in with `TRANS_BACK`, the countdown digits scale, the mode title takes over at `PREMATCH_INTRO_AT`). It landed in `d4e6678`; do not "add" it again.

**Phone fit** (`Session.safe_rect`, `main.gd:_layout_hud`, `menu.gd:_fit_stage`) — how the game meets the shape of an actual handset. Measured on the iPhone 15 this develops against: 2556x1179 landscape at 3x, which the `canvas_items`/`expand` stretch at a 1280x720 base turns into a **1561x720 viewport** — never the 1280x720 the project is authored in.

- **THE PICTURE FILLS THE DISPLAY; ONLY CHROME IS INSET.** The arena and the menu stage run edge to edge and under the notch and the home indicator, which is right — it is only a label that cannot be read there and a stick that cannot be reached. Insetting the whole picture is what both phone-fit P0s turned out to be: `MenuShell._fit_stage` fitted the entire stage into the safe rect and threw away **177 device px on each side and 63 at the bottom, 13.9% of the screen width**. It was invisible in development because the bars and `MenuUI.INK` are the same colour — it does not read as letterboxing, it reads as a small menu — and because a desktop window has no safe area to reproduce it with.
- **`Session.safe_rect(viewport)` is the ONE copy of that rectangle**, deliberately, because the menu and the match both need exactly these numbers and this is the `Arena.make_sun` situation again. Desktop gets the whole viewport; mobile gets the display safe area, scaled from window pixels into viewport pixels. It keeps a guard worth keeping: some platforms report the whole display rather than the window's safe area, so anything implausibly small is ignored rather than obeyed.
- **The menu's `chrome` node is what makes the split cost nothing.** `bg` and `brawler_view` sit on the stage and fill it; `home`, `screens_root` and `toast_column` hang off `chrome`, which `_fit_stage` insets. Every screen anchors FULL_RECT to its parent, so **no screen file knows the safe area exists**. `fx` is deliberately NOT in `chrome` — bursts should cross the whole picture, and `MenuScreen.center_of` / `MenuShell.fly_to` both compute destinations in STAGE space off `stage.global_position`, so reparenting it would silently offset every burst by the inset.
- **Nothing in the match HUD may be placed at a literal coordinate.** `main.gd:_layout_hud` runs on every viewport change and places all four labels and all three sticks off the safe rect. The four labels used to sit at 1280-authored coordinates, and `players_label` at x=1130 in a 430-wide box put its right edge at 1560 — so **the "N LEFT" counter was off screen in every desktop run the project ever did**. Two rules fell out: a label spans the full safe width and *aligns* inside it rather than sitting in a fixed-width box at a computed x, **because a Label grows RIGHTWARD past its minimum size to fit its text** and a right-aligned one in a narrow box walks off the edge on a long elimination line; and `center_label` needs a real width, since with a zero minimum size CENTER alignment centres text inside nothing and `position` is only its left edge.
- **Touch input still uses the whole glass.** `_unhandled_input`'s left-half/right-half split is on the raw viewport, not the safe rect — a thumb landing in the notch strip should still walk.
- **Type sizes convert differently in the two scenes, which is why "the text is small" is two problems.** Menu stage px x**0.364** = points; match viewport px x**0.546**. So the menu's utility tier (17-22) lands at 6.2-8.0 pt against Apple's 11 pt floor — about half — while the match HUD's labels sit at 12-39 pt and are fine. See `todo.md` 1.3: the menu half is a redesign of the type scale's deliberate hole, not a multiply.

**Touch controls** (`virtual_joystick.gd` = `TouchStick`, laid out by `main.gd:_layout_hud`, driven by `main.gd:_unhandled_input`) — three sticks, and every one of them both parked and floating.

- **They are on screen when nobody is touching them,** translucent, colour-coded: **blue** walks (left half), **red** shoots (right half), **gold** is the Super. They used to be invisible until touched, which is readable only once you already know they exist — nothing said the left half walks and the right half shoots, and the Super button was the only control you could see. Colour is the only thing telling them apart at a glance, so it has to be three that never read as each other.
- **They still float to the finger.** A touch anywhere in the stick's own region re-anchors the base under the thumb and the base slides home on release (`RETURN_TIME`). That is also what keeps a TAP unambiguous: `value` is zero at the instant of the press however far from home it landed, so a press-and-release is always a tap and never a full-deflection drag. The old Super button anchored its stick at the button and then fed it the touch position, so a thumb landing on the button's edge released a manually aimed Super it never asked for.
- **The Super's grab radius is much wider than the ring it draws** (`SUPER_GRAB_RADIUS` 118 against a 70 px ring, ~2.3x the old button's area). It can afford that because **an uncharged Super now falls THROUGH to the aim stick**: the old code swallowed the press, so a thumb that landed on the button in the half-second before it filled fired nothing at all, which is indistinguishable from a control that does not work.
- **There is no Super button.** `super_button.gd` is gone; the gold stick draws the charge dial and the star itself (`TouchStick.charge` >= 0 is what turns them on), so one circle does the job two overlapping ones used to.
- Sticks are hidden whenever `phase != PLAYING` or the player is down. That check sits **before** `_update_status`'s validity guard, because a Showdown elimination frees the player and would otherwise leave three parked joysticks under the results card.

**Tap-to-fire takes the nearest visible target**, for both an attack (`auto_aim_target`) and a Super (`main.gd:_super_target`) — same reach (`range * 1.1`), same wall and bush checks. The one difference is that a Super only ever picks a FIGHTER, never a loot box; a tapped attack falls back to a box so that tapping in a quiet corner opens crates instead of firing at nothing. Nearest is the only rule a player can predict without reading a marker, and a picker that re-ranks every tap sends consecutive shots at different people, which reads as the game arguing with you. The Super was briefly an expected-value picker — target worth (would this finish them, were you already trading with them via `Fighter.engaged_with`, are they wounded, are they close) times `_connect_odds` — and **it was removed on 2026-09-06 and should not come back**: a Super is aimed under pressure at the fighter you are looking at, and any rule that quietly prefers a different one is wrong at the moment it matters however good its reasoning is. `_tap_plan` returns `{kind, dir, target}` and has two cases left, `target` and `free`. **Every tap fires**, including a Super with nobody in reach, which shoots forward — there used to be a third case, `hold`, where it kept its charge instead, and a button that decides not to go off reads as a broken button rather than as restraint. The two `free` exceptions are deliberate and must survive any change here: Pop Off leaps the way you are already running (it is an escape) and Downhill sets off rather than firing at the wall in front of you. `tools/aim_probe.gd` prints what the picker chose and every candidate it chose between.

**A tap aims at where the target IS, never where it will be, and that is the whole design.** `_tap_plan` returns `target.global_position` flat. It briefly led the target perfectly (`main.gd:_aim_lead`, removed 7 Sep 2026) to fix a real fairness bug — bots led and the player did not — and that created a worse one: **a tap that leads is strictly better than aiming**, so drawing a lane with the stick became the slow way to do what the button did for free. Brawl Stars' auto-aim fires at the current position too, which is exactly why auto-aiming a moving target at range misses, why drag-aim is the skill, and why auto-aiming a thrower is a known bad play. It is also the rule already written down one paragraph up about the aim indicator: a preview that hands you the target "makes tapping the obvious play, when aiming is meant to be the thing you get good at" — a leading tap was that same lock-on, moved out of the preview and into the shot. **Do not put the lead back.** What it costs is exactly `SHOT_FEEL.md`'s `lead/hit` column — a tap misses a full-speed strafing target by that many body-widths at full range, linearly in range, so a tap still lands up close. Tap to brawl, aim to snipe. The fairness half is answered by bots leading only 0.00-0.40 of the correct amount (`BotBrain.LEAD_MATCH_*`), because the honest comparison is bot-aim against the player's DRAG, not against their tap: a bot has no tap, `_aim_point` IS its manual aim. `BotBrain.LEAD_SIM` (0.85) must NOT move — the sim wants bots that connect so `hits/atk` measures the weapon.

**A drawn shot can be called off, and that is not a hole in "every tap fires".** `TouchStick.peak` records the furthest a stick went during the CURRENT touch (reset by `begin`), because `value` alone cannot tell a finger that never left home from one dragged out to aim and brought back — both read zero at release. So `main.gd:_release_fire` has three cases: out and released is the lane you drew, never left home is a TAP and still auto-aims at the nearest target, out and brought BACK fires nothing. The rule survives because a tap is a gesture you did not aim, whereas drawing a lane and pulling it back is a second gesture performed deliberately — and it already tells you both ways, since the aim indicator vanishes and `_update_aim_detent` fires `aim_off` at the same `TAP_THRESHOLD` crossing. Use that constant and no other, or the tell and the behaviour drift. The check sits ahead of `_kick_instead`, so a Cup carrier who thinks better of a kick keeps the ball.

**The aim indicator only ever draws what a DRAG would do** (`main.gd:_draw_weapon_aim` — the weapon's real cone, lane, arc or weave, at the direction and reach the stick is asking for). A finger that is down but not yet dragged draws **nothing at all**, and that is the point: it used to preview the auto-aim's pick as a lane to the chosen fighter plus a ring around their feet, which is a lock-on marker — it hands you the target for free and makes tapping the obvious play, when aiming is meant to be the thing you get good at. That lane was also why **Nova's indicator turned into a thin straight line** part of the time: the line to a target is drawn identically for every kit and has nothing to do with the shape the weapon covers, so a shotgunner holding the stick saw a rifle's lane. Nobles Cup's carrier is the one exception (`_draw_kick_aim` still marks a tapped kick's destination) because that ring disambiguates a pass from a shot at goal — two different actions — rather than pointing out a target. `NS3_AIM_SHOW=attack|super` holds the drag indicator on at full deflection along the player's facing, since the indicator is otherwise only up while a finger is on the glass and `NS3_SHOTS` could never catch it.

**Match feel** — the effects layer, and the two rules it follows.

- **Effects are ImmediateMesh, not GPUParticles3D.** `shockwave.gd`, `melee_swipe.gd` and `hit_spark.gd` all rebuild a mesh per frame from vertex colours, unshaded, and free themselves. The camera is a fixed steep top-down, so a spray drawn flat in XZ reads from the only angle anyone sees, costs one draw call, and ships no art file — the same reasoning that makes every sound synthesized.
- **Two things will make a new effect invisible while rendering perfectly.** It needs `no_depth_test` if it sits on a fighter (a burst at chest height is hidden by that fighter's own body at a 60° camera pitch), and it needs to be **big**: the camera shows ~23 m across 1280 px, about 55 px/m, and a fighter is only ~70 px wide, so sub-metre geometry is a handful of pixels. `HitSpark`'s first pass at 1.5 m with darts spanning half of that was measurably spawning and completely unseeable.
- **A brief effect cannot be tuned from a screenshot.** Five frames is nothing. Hold it open — set the duration to ~1.5s temporarily, shoot it, then put it back. The same trick is how `Fighter.FLASH_ENERGY` was set.
- **Per-fighter visual state must not touch the GLB's own materials.** They live on a Mesh *resource* shared by every fighter wearing that model, so `_setup_model` duplicates each surface material and installs it as a surface override; the hit flash and bush fade drive those copies. The flash is **emission**, since `albedo_color` multiplies the texture and white is a no-op on a textured character. **Concealment is a TINT, not a fade, and that is load-bearing.** A character is a closed solid, so every per-fragment transparency mode shows you its own far side — the inside of a skull through a face, Sanjit's staff through his chest, shoes through shins. `TRANSPARENCY_ALPHA_DEPTH_PRE_PASS` is the textbook answer and is what this used, and **the prepass does nothing under the Forward Mobile renderer this project runs on**: every model came out a smear the moment it stood in a bush, and it shipped that way because it was never shot standing in one. `TRANSPARENCY_ALPHA_HASH` does fix the sort (opaque pass, stochastic discard, real depth) but dithers, and at any alpha low enough to read as hidden the sparkle on a moving fighter is worse than the bug. So a concealed fighter stays opaque and multiplies its albedo by `CONCEAL_TINT` instead — no sorting, no dithering, and the tell still reads because the foliage around you opens up at the same time. `set_concealed` runs every physics frame for every fighter, so `Fighter._conceal_applied` still gates it to real transitions.
- **`main.gd:clear_in_flight()`** frees everything a weapon has put in the air (and `DisconnectZone`/`Shockwave`/`MeleeSwipe`), shared by `start_match` and `CupMode.kickoff` so the lists cannot drift. It deliberately excludes the Ball, which a kickoff re-places. Freeing a `Boomerang` is also what returns Sanjit's staff (`boomerang.gd:_exit_tree`).
- **Going down and coming back are code, not clips.** No GLB here ships a death or a hit animation — the models carry idle, walk, run and an attack — so `Fighter._pop_out` swells the body for a beat and bursts it, and `_play_arrival` grows a bubble around a fighter scaling up out of nothing and then pops it. Both act on `_model` (or the capsule), never on the fighter: `rotation.y` on the fighter is its FACING and aim, bars and the ball's carry point all read it. A first pass toppled the body onto the floor instead; a pop is better because at a 60° camera a body lying down is a shape you have to read, and the point of the moment is that it is instant. The bubble is additive and never writes depth, so the fighter growing inside is never hidden by it, and its fresnel is deliberately far thicker than a real one — at 55 px/m a shell a few degrees wide is a couple of pixels, and the first version was invisible against the pale end zone a Cup respawn happens in. A Cup knock-out hides the body at the END of the pop rather than on the frame of the hit; `fighter_bars.gd:77` already skips a dead fighter, so no full health bar hangs over it.
- **A Nobles Cup death washes the screen red and counts you back in** (`main.gd:_build_down_overlay`, `_update_down_overlay`, `DOWN_SHADER`). Two things it learned: a FLAT red pane at an alpha low enough to keep the pitch readable does not read as red at all — over green it composites to olive and the screen just looks dirty — so it is a vignette, saturated at the edges and nearly clear in the middle; and the counter sits in the lower third rather than dead centre, because `center_label` is there and a kickoff's "GO!" printed straight through it. It is Cup-only: a Showdown death has nothing to count to and raises the results card instead. It also cannot reach over Cup's own scoreboard, which is on its own CanvasLayer above the HUD — the same thing `_show_results` works around, and desirable here, since the score and clock stay legible through the wash.
- **`main.gd:focus_camera(at, seconds)`** points the camera somewhere other than the player for a beat, on a slower lerp than the player follow. Cup uses it on a goal, inside the kickoff freeze that already holds input.

**Match lineup** (`main.gd:lineup_kits` / `:next_bot_name`, called from `start_match` and `CupMode.build_match`) — who you actually fight.

- **Kits are dealt from a shuffled pool without replacement, never `pick_random()` per slot.** Per-slot random put two of the same character on one Nobles Cup team about a third of the time and dealt Showdown the same fighter three or four times. `lineup_kits(count, first)` refills the pool when it runs dry rather than capping, so Showdown's ten slots against nine kits fill nine of them with nine different characters and only the tenth can echo. **Cup deals one lineup PER SIDE**, so no character repeats within a team but the same character may line up opposite themselves — Brawl Ball's own rule, and deliberate. `first` (the player's kit) is dealt out of the first pass only, and comparison is by NAME: `player_kit()` returns Session's own copy of the dictionary, not one of the instances `Kits.all()` builds fresh on every call, so `==` would never match.
- **Bots wear usernames** from `game.json`'s `opponents` (56 of them, via `MenuData.opponent_names`), dealt without repeats from a per-match shuffle that `start_match` clears. `display_name` prints in four places at once — the versus cards, the elimination feed, the nameplate over the fighter and the results table. **`NS3_SIM` keeps the old kit-based naming on purpose**, because `[sim] match 12/60: Kovacs 4 wins` is the line that has to stay readable.
- **The Cup kickoff spots are shuffled once into `CupMode._lineup`, and `build_match` and `kickoff` both read that array** — never `arena.team_spawns` directly. The player is always team 0 slot 0, so without the shuffle they opened every single match on the same tile at the left end of the row. The two callers agreeing is load-bearing: when they disagreed, fighters spawned on top of each other and the capsule depenetration fired them off the pitch and several hundred metres into the air.
- **`fighter_bars.gd`'s stack hangs UP from `HEAD_OFFSET`, not down.** It used to hang down from 3.4 m, so the clearance had to be re-earned every time a row was added, and by the time the health bar, the ammo pips and Hammy's heat pips were stacked it was being painted across the model's face. The anchor is now the top of the head (2.75 m) plus a fixed `HEAD_CLEAR` in pixels, and every row grows upward from there, which makes a new row free. Anything added below the pips has to be counted into `below`.

**Scale: ONE TILE IS ONE FIGHTER.** `Kits.TILE` (1.30 m) is exactly `2 * Kits.FIGHTER_RADIUS`, so "tiles" and "body-widths" are the same unit, as they are in Brawl Stars ("a Brawler's hitbox is slightly larger than a single tile of cover... shown by the ring around their feet"). Every figure they publish — range 8.33, movement 2.40/s, projectile 12.0/s — is denominated in it, so ours compare by reading rather than converting. Rescaled 7 Sep 2026 from a 2.0 m tile; see `SHOT_FEEL.md` §10 for the full pass. Four things follow, and each has bitten already:

- **Changing `TILE` means changing every `X * TILE` in the project**, because such a value keeps its number and silently changes its meaning. It also means regenerating the Showdown map and re-authoring the Cup pitch.
- **A fighter is exactly as wide as a tile, so a one-tile corridor has ZERO clearance** and a fighter jams in it. `Arena.TILE_COLLISION_SHRINK` (0.75) insets terrain *collision* inside the tile it is *drawn* on, which is what makes those corridors passable — Brawl Stars does the same, its movement collider being smaller than its hitbox ring. **Inset the wall, never the fighter**: the fighter's capsule is also its hurtbox (`projectile.gd` sweeps against it), so narrowing it would shrink `hit_width`, silently retune every `lead/hit` figure, and make the feet ring a lie. **`NS3_SIM` cannot see this class of bug** — bots path on the ASCII grid and route around gaps they cannot fit through, so the balance table stays healthy while a player wedges. `tools/fit_probe.gd` is the check (`NS3_MAP=showdown Tools/godot.sh --path godot --headless --script res://tools/fit_probe.gd`); run it after touching `TILE`, `FIGHTER_RADIUS`, `TILE_COLLISION_SHRINK` or either map.
- **Speed sits just above Brawl Stars parity** — `SPEED_NORMAL` 3.60 m/s = 2.77 tiles/s against their 2.40, the other four tiers derived from it. Exact parity (3.12) was tried and played as "genuinely moving in slow motion" — though most of that turned out to be oversized models, so **judge speed and `MODEL_SCALE` together, never one alone**: perceived pace is body-LENGTHS per second. Tune that one constant; every projectile speed is a multiple of a tier, and `lead/hit` has no move-speed term so aiming difficulty does not move. The floor is the run clips: stride is `velocity / RUN_CLIP_SPEED` clamped at 0.35, and `SPEED_VERY_SLOW` already lands at 0.357.
- **Time constants stay, distance-per-second constants scale, tile-denominated distances multiply.** Knockback is the trap: `IMPULSE_TRAVEL` makes every `knockback` a displacement with a fixed ~0.109 s decay, so it is an impact and stays in metres. The ball is travel, so it time-dilated — speed, `STOP_SPEED` *and* `DRAG` all scaled, which preserves `kick_range()` exactly while stretching the clock.

**Every fighter wears a hitbox ring** (`fighter.gd:_setup_hitbox_ring`), in every mode, not just Nobles Cup. The torus straddles `FIGHTER_RADIUS`, so its mid-line is 1.40 m against a 1.30 m tile. It takes the team colour in Cup and the kit colour in Showdown — the same split `fighter_bars.gd` makes for health bars. It is the only thing that makes the tile-is-a-fighter unit legible while playing, because the models are roughly half the capsule's width.

**GDScript gotchas:** `:=` cannot infer types from ternaries or cross-script members — annotate; never `class_name` anything Godot ships natively (a native `VirtualJoystick` silently shadowed ours — members vanish with only runtime "invalid access" errors; ours is `TouchStick`).

**Godot gotchas beyond GDScript itself:** a **1-pixel-wide `ImageTexture`** in a `TextureRect` (`EXPAND_IGNORE_SIZE` + `STRETCH_SCALE`) drew nothing at all, with no error — `GradientTexture2D` is the working way to lay a gradient scrim over art, and it is less code. Driving a Control's own `size` from its `resized` signal **recurses** and trips a `_set_size` error, so a rotated banner cannot size itself off its parent that way.

**Character model pipeline:** Meshy exports GLB — always run `python3 Tools/fix_meshy_glb.py <file.glb>` on a fresh export before committing (fixes broken material export, +Z facing, and adds the missing Idle clip); cleaned models live in `Assets/3D/` (see its README) and get copied into `godot/assets/` when wired into a kit. The synthesized Idle is a stance, not the rest pose: `--idle-from CLIP:SECONDS` takes a frame of an existing clip as the base, `--idle-aim BONE:x,y,z` points a bone (its +Y) along a world direction (parents before children; the model faces **-Z**, so "forward" is negative z) and `--idle-spin BONE:ax,ay,az:deg` turns one about its own axis; `--replace-idle` drops the old Idle so all of that can be re-run on an already-fixed file. Ayaan's is `Punch_Combo_3` at 0.0 (symmetric feet, fists) with both arms re-aimed down-forward to hip height and an 8° forward lean — the guard frame it started from read as hands-up surrender on the home screen. Look at a stance with `tools/pose_probe.gd` (`NS3_POSE_KIT=ayaan NS3_POSES="Idle:0,Idle:0:front"`; `front` is the menu stage's straight-on view) before wiring it. A model whose fighter throws what it holds (Sanjit's staff) is re-exported with `--split-held-item left|right`, which carves the item into a `held_item` node; `fighter.gd:set_held_item_visible` hides it while the thrown copy flies and `boomerang.gd:_exit_tree` puts it back. Meshy's run/attack clips drop the hips below the rest pose, so `fighter.gd` calibrates each model's idle foot height at spawn and lifts the model per-frame by however far the lowest foot bone sinks below it; `Godot --path godot --headless --script res://tools/foot_probe.gd` prints the per-clip sink and lift for every model.

**Worn gear** (`kits.gd` `gear`, `fighter.gd:_setup_gear`): a prop bolted to bones for part of a clip — Ayaan's skis through the Downhill jump (`"on": "super"`), Anders' hacky sack on his kicking foot from the cast until the kick lands (`"on": "attack"`, then `main.gd:_launch_sack` throws the same model from `gear_global_position()`). A piece is either a named node of the gear GLB (`{"node": "left", "bone": "LeftFoot"}` — `fix_meshy_glb.py --split-halves` carves a pair into `left`/`right`) or, with no `node`, the whole model fitted to `radius` by `Fighter.fit_ball` (which is also what `hacky_sack.gd` uses for the thrown copy when `weapon.model` names a GLB). Each piece hangs off a `BoneAttachment3D` and its rest transform is **solved in world space** — `skeleton.global_transform * get_bone_global_rest(bone)` inverted against the pose the kit asks for in model space. Solving in skeleton space looked right on the ground and put the skis a hundred metres away at the apex of the jump, because Meshy armatures carry a 0.01 scale that a child of the skeleton inherits. `rotation_deg`/`scale`/`offset` are in the model's frame with `offset.y` an absolute height. `Loading.to_match` preloads gear and `weapon.model` GLBs beside the bodies for the same reason it preloads them. **Judge it with `tools/gear_probe.gd`** (`NS3_GEAR_SHOTS="ayaan:Jump_Over_Obstacle:0.8,anders:Kick_a_Soccer_Ball:0.3"`), which runs the identical solve on a frozen frame — the live wind-up is 0.12 s long.

**Arena screenshots without playing a match:** `Godot --path godot --script res://tools/render_map.gd` (**not** `--headless` — the dummy driver writes empty PNGs). `NS3_MAP_KIND=overview` shoots the whole map on the match's own light rig, which is how you judge a floor or a pond all at once and is the frame the events screen's map thumbnails will want; `NS3_MAP_KIND=game` shoots through `Arena.MATCH_CAM_*`, the real match lens, pointed at `NS3_MAP_AT="col,row"`. **Does a fighter FIT?** `NS3_MAP=showdown Tools/godot.sh --path godot --headless --script res://tools/fit_probe.gd` places a fighter's own capsule at every open tile and asks the physics server whether it overlaps. Because `Kits.TILE == 2 * Kits.FIGHTER_RADIUS`, a one-tile corridor is exactly as wide as a fighter and passability rests entirely on `Arena.TILE_COLLISION_SHRINK` — **and `NS3_SIM` is blind to it**, since bots path on the ASCII grid and route around gaps they cannot fit through, leaving the balance table looking healthy while a player wedges. Run it after touching `TILE`, `FIGHTER_RADIUS`, `TILE_COLLISION_SHRINK` or either map. It was validated by reintroducing the bug it was written for (849 of 2625 open tiles unfittable at shrink 1.0, zero at 0.75) — an instrument that cannot fail is worthless.

**Power-cube performance:** `main.gd` must keep `power_cube.glb` preloaded. Loading the 21 MB source scene inside `_spawn_cube` puts disk/texture work on the loot box's fatal-hit frame and causes a visible freeze. The extracted 4096×4096 base-color and metallic/roughness textures are intentionally capped at 512 via their `.png.import` files (about 582 KB imported total instead of 16.6 MB); preserve that cap and reimport after changing either texture.

**iOS export** — use `Tools/export_ios.sh`, which already sets the environment the export needs. Templates live at `~/Library/Application Support/Godot/export_templates/4.7.2.stable/ios.zip`; the preset has `export_project_only=true`, so what you want out of it is `build/ios/noblestars3d.xcodeproj`.

- **`export_presets.cfg` has NO comment syntax that survives — `#` lines silently eat the key that follows.** It is parsed by Godot's ConfigFile, which knows `;` and not `#`, and the failure is quiet: a `#` block written between two options had the first one read and the second one dropped, so a setting that is plainly there in the file has no effect. The editor also rewrites this file and would strip comments anyway. **Keep the preset bare and put the reasoning here.**
- **The launch storyboard defaulted to `contentMode="center"`, which is why a fresh install came up SMALL.** Godot writes the same 1920x1080 splash to both `@2x` and `@3x`, so at @3x iOS reads it as 640x360 points on an 852x393 point screen and draws it smaller than the display with a border all round — and because iOS holds the storyboard until Godot's first frame, a cold first launch sits on it for several seconds and it is very visible. `storyboard/image_scale_mode=2` (Scale to Fit, `scaleAspectFit`) matches what the engine boot splash does a moment later, so the handoff is seamless; Scale to Fill would crop ~9% off the bottom of a 19.5:9 screen, which is where the title and loading bar are anchored. **Verify by grepping `contentMode` in `build/ios/noblestars3d/Launch Screen.storyboard` after an export** — the enum is `Same as Logo,Center,Scale to Fit,Scale to Fill,Scale`, readable out of the Godot binary with `strings`.
- **The export REQUIRES `rendering/textures/vram_compression/import_etc2_astc=true`** in project.godot. Without it validation fails with an EMPTY error message.
- **Godot's `targeted_device_family` enum is 0=iPhone 1=iPad 2=both**, which is not Apple's numbering.
- **Set `DEVELOPER_DIR` when exporting.** `xcode-select` points at CommandLineTools, and Godot shells out to `xcodebuild` internally, so the export dies at "Making .xcarchive" with `tool 'xcodebuild' requires Xcode`. The `.xcodeproj` is already written by that point, so the failure is cosmetic — but the exporter reports the whole export as failed, which reads like a real problem.
- **The pbxproj placeholder repair is no longer needed.** Older templates left six unreplaced `$additional_pbx_*`/`$pbx_embeded_frameworks` lines that had to be deleted before `xcodebuild` would parse the project. 4.7.2 emits zero. `export_ios.sh` still checks and reports.
- **Simulator builds are blocked upstream**: godotengine/godot#118161 — 4.6.2+ templates ship simulator `libgodot.a` as x86_64-only and Xcode 26 has no Rosetta simulators; test on a real device until fixed templates ship.

**Getting it onto a phone.** `xcrun devicectl` is the tool, and `connectionProperties` from `xcrun devicectl list devices --json-output <path>` is the only signal that tracks reality: `transportType` (`None` = not connected), `pairingState` (`pairingInProgress` = a Trust prompt is waiting on the phone) and `tunnelState`. **`system_profiler SPUSBDataType` does NOT enumerate iPhones on this Mac** — it reported zero the entire time a wired transport was live, and reading it as ground truth led to a long, wrong hunt for a bad cable. Also do not grep device state for `available`: `unavailable` contains it.

**Signing: `No Account for Team` has had TWO causes here, and the second one hid behind the first.** The one to check now is the **team id in the preset**: `application/app_store_team_id` named `KJDG3J6ZYY`, which is a.carlson14@gmail.com's free personal team, while the account actually develops under the paid team `S7AT3UP8R4` ("ANDREW DWIGHT CARLSON"). Godot wrote the wrong id into `DEVELOPMENT_TEAM`, so the archive step really did have no account for the team it was naming. Corrected in the preset on 2026-09-05, and `Tools/export_ios.sh` now runs end to end — `** EXPORT SUCCEEDED **`, no errors, an `.ipa` on disk. Tell the two apart by reading the profile rather than the error: `security cms -D -i <app>/embedded.mobileprovision` prints `TeamIdentifier` and `TeamName`, and that is the team the preset has to name.

**A successful export still PRINTS `KJDG3J6ZYY`, and it is not the bug above.** `xcodebuild`'s log names the signing certificate — `Signing Identity: "Apple Development: a.carlson14@gmail.com (KJDG3J6ZYY)"` — and that parenthetical is the CERTIFICATE's identifier, not the team the build is signed for. Read against the paragraph above it looks exactly like the preset regressing to the free personal team, which is a false alarm that has already cost one session a detour. The profile is what settles it, and on the 2026-09-06 export it said `TeamName ANDREW DWIGHT CARLSON`, `TeamIdentifier S7AT3UP8R4`, `TimeToLive 365`, expiring 2027-09-05 — the paid team, the year-long profile. Check it out of the `.ipa` rather than hunting for an `.app`, which the project-only export does not leave in `build/ios/`:

```sh
cd $(mktemp -d) && unzip -q -o <repo>/build/ios/noblestars3d.ipa 'Payload/*/embedded.mobileprovision'
security cms -D -i Payload/*/embedded.mobileprovision > prov.plist
/usr/libexec/PlistBuddy -c 'Print :TeamIdentifier' -c 'Print :TimeToLive' prov.plist
```

The older cause, which is the one the rest of this section is about: **a signing-identity CONFLICT, not a missing account.** Godot writes `CODE_SIGN_IDENTITY = "Apple Distribution"` into the Release configuration while also setting `CODE_SIGN_STYLE = Automatic`. Xcode will not reconcile those, and the conflict poisons provisioning for the whole target — including Debug — which surfaces from the command line as `No Account for Team "<id>"` and `No profiles for '<bundle>' were found`. Both point at the account, and the account is fine. An evening went into that misdirection; what identified it was the Signing & Capabilities pane in the Xcode GUI, which says plainly `noblestars3d has conflicting provisioning settings`. **When signing fails, open the project and read that pane before touching accounts.**

The fix is in the preset, so re-exports stay correct. Development signing on **both** configurations is right for the side-load workflow this has used until now:

```
application/app_store_team_id="S7AT3UP8R4"   # the PAID team, not KJDG3J6ZYY
application/code_sign_identity_debug="Apple Development"
application/code_sign_identity_release="Apple Development"
application/export_method_release=1     # development, not App Store (0)
```

With that, `xcodebuild -allowProvisioningUpdates` signs and builds with no GUI step at all.

**⚠ Beta changes this, and the change walks back toward the trap above.** `ROADMAP.md` commits to a **TestFlight closed beta**, which cannot be fed a development-signed build: it needs `export_method_release=0` and `Apple Distribution` on Release — which is exactly the identity whose conflict with `CODE_SIGN_STYLE = Automatic` cost the evening described two paragraphs up. So the sentence "Development signing is right for both configurations" is true of side-loading and **false of TestFlight**, and whoever makes that switch should expect the `No Account for Team` symptom to reappear pointing, once again, at the wrong thing. Do it in this order: change Release only, leave Debug on `Apple Development` so device installs keep working, then open the generated project and read the **Signing & Capabilities** pane before believing any command-line error. The side-load path must keep working throughout — it is how the phone-fit P0s get tested. Note that `~/Library/MobileDevice/Provisioning Profiles/` can be EMPTY and `defaults read com.apple.dt.Xcode IDEProvisioningTeams` absent even on a build that then succeeds — they look like the signing health check and are not one.

**Use `Tools/device_install.sh` and `Tools/device_shot.sh`.** Between them the
whole handset loop — export, build, install, run with debug hooks, screenshot,
pull the PNG back — is two commands and needs no Xcode and **nobody looking at
the phone**:

```sh
Tools/device_install.sh                                     # export + xcodebuild + install
Tools/device_shot.sh --out shots NS3_KIT=nova NS3_SHOTS=run:3,9
Tools/device_shot.sh --out shots NS3_MENU_SHOT=m.png NS3_MENU_SCREEN=roster
```

**This is the single most useful thing to know about testing here**, because
ROADMAP.md is written around the assumption that a device screenshot is a round
trip through Ryder and is therefore the slowest loop in the project. It is not,
and it works because three facts compose: `devicectl device process launch -e
'{"K":"V"}'` passes environment variables in, so **every `NS3_*` hook works on
the phone**; `NS3_SHOTS`/`NS3_MENU_SHOT` resolve a relative path against
`user://`, which on iOS is the app's `Documents/`; and `devicectl device copy
from --domain-type appDataContainer --domain-identifier com.ryder.noblestars3d`
reads that directory for a development-signed app. Four sharp edges, all
handled inside the scripts:

- **`--console` hangs.** It attaches and never returns even after the app has
  exited and written its file. Poll for the file instead — which is also the
  real completion signal, since `NS3_SHOTS` quits the game once it has written
  the last frame.
- **`copy from --destination` must be a FILE path.** A directory fails with
  `Cannot open destination file …: Is a directory`.
- **Pick the device out of `--json-output`, never the printed table.** The State
  column is prose that changes under you — `connected` one minute,
  `available (paired)` the next — and per the warning above, `unavailable`
  contains `available`. The test is `connectionProperties.transportType` being
  present and `tunnelState != "unavailable"`; a `disconnected` tunnel reconnects
  on demand and is fine.
- **There is no delete in `devicectl`**, so shots pile up in the container. Use
  a fresh name per run rather than assuming one is free.

**Xcode keeps TWO `Debug-iphoneos` trees and installing the wrong one looks like
a signing failure.** `<derived>/Index.noindex/Build/Products/Debug-iphoneos/`
holds the indexer's stub `.app`, whose `Info.plist` has no `CFBundleIdentifier`;
`devicectl` refuses it with `Failed to get the identifier for the app to be
installed`. It is one level deeper than the real bundle, so the `-maxdepth 6`
form below matches either, whichever `find` reaches first. Use `-maxdepth 5
-not -path '*Index.noindex*'`, as the script does.

By hand, if a script is not to hand:

```sh
APP=$(find ~/Library/Developer/Xcode/DerivedData -maxdepth 5 -name 'noblestars3d.app' \
    -path '*Debug-iphoneos*' -not -path '*Index.noindex*' -print -quit)
xcrun devicectl device install app --device <udid> "$APP"
xcrun devicectl device process launch --device <udid> com.ryder.noblestars3d
xcrun devicectl device info processes --device <udid> | grep noblestars3d   # still alive?
```

That last line matters: a Godot iOS build can launch and die immediately on a texture or shader problem, and the launch command reports success either way. **This signs under a PAID developer account**, so the profile is good for a year (`TimeToLive 365`, read off `embedded.mobileprovision`) — the 7-day expiry that forces a weekly reinstall is a free personal team, and does not apply here. **`devicectl` needs `DEVELOPER_DIR` too**, exactly like the export: `xcode-select` points at CommandLineTools, so a bare `xcrun devicectl` fails with `unable to find utility "devicectl"`. And an install onto a phone that has never run a development build stops with `Developer Mode is disabled` — that is Settings > Privacy & Security > Developer Mode on the phone, followed by a restart, and it cannot be done from here.
